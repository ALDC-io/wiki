# core_api v1 Domain Model

> *2021 schema snapshot. The current (v2) CosmosDB collection schema lives in [[cosmosdb-schema]]. This page documents the v1 structures for historical reference and legacy integration context.*

The v1 domain model underpins the original ALDC scheduling/extraction pipeline: Routine → Queue → Schedule → Session → Schema. It was designed before the work_template/work_partition split in v2.

**Key v1 → v2 differences:**
- v1 uses `Routine` + `work_activated` for partition scheduling; v2 uses `work_template` + `work_partition`
- v1 `account` emphasises `keystore_prefix` and Snowflake short_code; v2 adds contract_periods, billing fields, tier
- v1 `session` structure is broadly compatible with v2 but lacks the `events` array (uses separate session_event collection)

## Common Document Attributes (v1)

Source: CORE/537002029.

All v1 CosmosDB documents share:

| Field | Description |
|---|---|
| `id` | Document ID — generated by CosmosDB or API |
| `<object>_id` | Foreign-key reference to a named object |
| `connector` | Connector code assigned by the Router class |
| `topic` | Topic assigned for the task instance |
| `option` | Options dict, unique per connector |
| `status` | `"init"` → `"complete"` → `"zombie"` (zombie set by schedule validation trigger) |
| `payload` | Generic dict for telemetry or task-associated data |
| `comment` | Free-text notes |
| `datetimestamp_init_utc` | Unix timestamp (UTC), creation |
| `datetimestamp_update_utc` | Unix timestamp (UTC), last update |
| `datetimestamp_complete_utc` | Unix timestamp (UTC), completion |
| `duration_init_complete` | Seconds between complete and init timestamps |

| Field | Type | Description |
|---|---|---|
| `id` | string | 8-char hex, developer-assigned |
| `keystore_prefix` | string | Prefix for OS-level keystore: `"aldc_" + account_id` |
| `short_code` | string | Human-readable code; used as Snowflake client database name |
| `full_name` | string | Full legal client name |
| `tier` | enum | `XS`, `S`, `M`, `L`, `XL`, `C` |

| `region` | enum | `"canada_central"`, `"usa_west"`, `"usa_east"` + planned others |
| `storage_prefix` | string | Storage account prefix within provider |

```json
  "tier": "XS",

  "provider": "azure",
  "region": "canada_central",

}
```

Source: CORE/540114985.

| Field | Type | Description |
|---|---|---|
| `id` | string | Connector code (e.g., `"sqlserver_v1"`) — used throughout core_api |

## Template System & Queue Storage (v1)

Source: CORE/522191103.

Events are scheduled by Core and consumed by agents (Connector Extractor, Warehouse Processor, Report Trigger, Metadata Manager) via Azure Queue Storage.

**Templates** define static parameters for a schedule sequence: topic, connection, table/query, filter/partition scheme. One template covers one source table or partition set.

**Partition Activation (`work_activated`):** partitions are created from template definitions and stored as `work_activated` documents, then queued as messages for agents. Compare with v2 `work_partition` collection.

### Template document (v1)

Key fields: `account_id`, `connection` (inline object with server/port/uid/pwd/etc.), `options` (table, schema, primary_key, table_name, category, filter, fields), `connector`, `topic`, `retry_default`, `retry_doubling`, `partition_scheme`.

> *Note: v1 stored connection credentials inline in the template (`connection.uid`, `connection.pwd`). v2 separates these into `work_connection` referenced by `connection_id`.*

Partition scheme structure is consistent with v2 — see [[cosmosdb-schema]] § Work Template Collection § partition_scheme.

### Activated partition document (v1 `work_activated`)

```json
{
  "template_id": "84259524-6d80-47b8-b486-2a1bc0c145b5",
  "account_id": "d77e717c",
  "status": "active",
  "partition": {
    "partition_keys": {"field": "date_last_modified_gmt", "key": "2021-04-07"},
    "filter": [
      {"field": "date_last_modified_gmt", "operator": "greater_equal", "value": "2021-04-07 00:00:00"},
      {"field": "date_last_modified_gmt", "operator": "less", "value": "2021-04-08 00:00:00"}
    ]
  },
  "retry_next": 300,
  "datetimestamp_init_utc": 1618743306.11,
  "datetimestamp_last_utc": 1618743485.02
}
```

**v1 → v2 mapping:** `work_activated` ≈ `work_partition`. Field names largely compatible; v2 adds `in_queue`, `hash_result_last`, `run_count`, `queue_messages`.

## Schema Collection (v1)

Source: CORE/540115003.

Stores the warehouse schema currently in the destination (Snowflake) per connector/topic/category/table combination. A new version is written whenever primary keys or column structure changes.

| Field | Type | Description |
|---|---|---|
| `id` | UUID | CosmosDB-generated |
| `account_id` | string | Owner |
| `version` | int | Incremented on each schema change |
| `current` | boolean | Whether this is the active version |
| `connector` | string | Connector type |
| `topic` | string | Topic |
| `category` | string | Sub-category |
| `table` | string | Table name |
| `schema` | list[dict] | Column defs: `name`, `native_dtype`, `dw_dtype` |
| `primary` | list[string] | Primary key fields |

**Type mapping:** `object` → `varchar`, `datetime64[ns]` → `datetime`, `float64` → `float`, `int32` → `bigint`.

> **Key pitfall:** Multiple schema versions coexist per connector/topic/category/table. The `current` flag marks the active one. Stale versions can cause warehouse load failures — see [[CosmosDB]] § Key pitfall.

## Merge Strategies & History Tracking (v1)

Source: CORE/701956097.

Four strategies for merging staging data into permanent Snowflake warehouse tables:

| Strategy | Primary Key | Deletes | History |
|---|---|---|---|
| **Heap** | Not required | No (append-only) | Disabled (columns present but static) |
| **Add** | Required | No | Optional |
| **Full** | Required | Yes (marks deleted) | Optional |
| **Key Sync** | Required | Yes (key comparison only) | Optional |

### Strategy details

**Heap:** Append-only. No UPSERT. Use for immutable event data.

**Add:** INSERT new rows + UPDATE changed rows. No deletes. Use for additive streams (event logs, transactions). Often paired with Key Sync for delete detection.

**Full:** Complete reconciliation — INSERT, UPDATE, and MARK DELETED. Source must provide entire payload snapshot. Use for dimensions/fact tables with full refresh.

**Key Sync:** Compares only primary key columns between source and destination; marks rows missing from source as deleted. Cheap on data transfer; run at lower cadence than Add.

### History keeping (SCD Type 2)

When `merge_history = true`, system adds and manages metadata columns:

| Column | Purpose |
|---|---|
| `___ALDC___GLOBAL_SCHEDULE_ID___` | Schedule run that wrote/last-updated the row |
| `___ALDC___GLOBAL_SESSION_ID___` | Session that processed the row |
| `___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___` | When this version became current (immutable per version) |
| `___ALDC___GLOBAL_HISTORY_TIMESTAMP_END___` | When superseded (`NULL` while current) |
| `___ALDC___GLOBAL_HISTORY_CURRENT___` | `1` = current, `0` = historic |
| `___ALDC___GLOBAL_HISTORY_DELETED___` | `0` = active, `1` = deleted |
| `___ALDC___GLOBAL_ROW_VERSION___` | Version counter per natural key |

**Heap cannot use history tracking.** All other strategies support both `merge_history = true` and `false`.

See [[cosmosdb-schema]] § Work Template Collection for the `merge_strategy` / `merge_history` fields on the current v2 template.
