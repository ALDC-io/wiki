# Post Deployment Troubleshooting - Iteration 2


Good — this gives us a clear picture. The view is the filter, not a task issue.

  The numbers tell a specific story

  - Prod share has 1.58M raw Amazon order lines — plenty of data, back to July 2023
  - View outputs only 25K Amazon orders — massive filter happening in the view logic
  - Live view matches the materialized table (24,456 vs 24,305 USD — tiny drift from timing, both ~25K)

  So Test's materialized table is a true reflection of what the view produces. No task issue. The question is: what is filtering 95%+ of the records out?

  My top hypothesis: the Amazon↔SellerCloud dedup logic

  Look at sales_dim_order_base.sql:254-265 — the Amazon UNION leg has this:

  LEFT JOIN   -- Limit such that Amazon data is preferred unless Order and Order Line are both present in Seller Cloud
  (
      SELECT DISTINCT SELLERCLOUD_ORDERS.ORDERSOURCEORDERID
      FROM SELLERCLOUD_ORDERS
      INNER JOIN SELLERCLOUD_ORDERITEM ON (SELLERCLOUD_ORDERITEM.ORDERID = SELLERCLOUD_ORDERS.ID)
      WHERE SELLERCLOUD_ORDERS.ORDERSOURCE IN (20, 4)   -- Amazon and Fulfilled by Amazon (FBA)
  ) AS ORDER_LIMIT ON (ORDER_LIMIT.ORDERSOURCEORDERID = AMAZON_ORDERS.AMAZON_ORDER_ID)
  ...
  WHERE ORDER_LIMIT.ORDERSOURCEORDERID IS NULL

  This says: keep Amazon orders ONLY if they DON'T exist in Seller Cloud (Seller Cloud is the system of record when both are present — dedup logic).

  The likely cause of the drop: before today, Test probably read from local TEST_DG1_GEP.SELLERCLOUD_SQL.* tables that had limited data. Now via the prod share, Seller Cloud has the full
  production dataset — so far more Amazon orders get matched and deduped out, leaving only the small residual that only exists in Amazon and not in SC.

  Verify with these queries

  -- How many distinct Amazon orders in the raw prod share?
  SELECT COUNT(DISTINCT AMAZON_ORDER_ID) AS amazon_distinct_orders
  FROM PROD_DG1_GEP.AMAZON.CURRENT_REPORT_ALL_ORDERS;

  -- How many Amazon-sourced orders exist in Seller Cloud (these cause the dedup)?
  SELECT COUNT(DISTINCT ORDERSOURCEORDERID) AS sc_amazon_orders
  FROM PROD_DG1_GEP.SELLERCLOUD_SQL.CURRENT_MAIN_ORDER
  WHERE ORDERSOURCE IN (20, 4);

  -- How many Amazon orders are ALSO in Seller Cloud (deduped out)?
  SELECT COUNT(DISTINCT A.AMAZON_ORDER_ID) AS overlap
  FROM PROD_DG1_GEP.AMAZON.CURRENT_REPORT_ALL_ORDERS A
  INNER JOIN PROD_DG1_GEP.SELLERCLOUD_SQL.CURRENT_MAIN_ORDER S
      ON S.ORDERSOURCEORDERID = A.AMAZON_ORDER_ID
  WHERE S.ORDERSOURCE IN (20, 4);

  -- How many Amazon orders are NOT in Seller Cloud (should match the ~25K output)?
  SELECT COUNT(DISTINCT A.AMAZON_ORDER_ID) AS amazon_only
  FROM PROD_DG1_GEP.AMAZON.CURRENT_REPORT_ALL_ORDERS A
  LEFT JOIN PROD_DG1_GEP.SELLERCLOUD_SQL.CURRENT_MAIN_ORDER S
      ON S.ORDERSOURCEORDERID = A.AMAZON_ORDER_ID
      AND S.ORDERSOURCE IN (20, 4)
  WHERE S.ORDERSOURCEORDERID IS NULL;

  Expected result if my hypothesis is correct:
  - amazon_distinct_orders ≈ some large number (maybe 400K-700K distinct orders from 1.58M line items)
  - overlap ≈ most of that number
  - amazon_only ≈ 25K (matches your view output)

  If amazon_only lands around 25K, mystery solved — the dedup is doing exactly what it's designed to do, and the volume drop is expected behavior from GP-207 deploying to Test (not a GP-200      
  regression).

  If that hypothesis is confirmed

  The pre-snapshot was an artifact of Test previously having less Seller Cloud data than prod, which made Amazon look "larger" in the dedup output. With the prod share now providing full Seller  
  Cloud data, the numbers reflect reality. This is not a data loss — the data is all still there, it's just correctly attributed to Seller Cloud instead of being duplicated in the Amazon side.   

  To prove nothing is lost, also run:
  -- Total orders (SC + Amazon combined) in the new materialized table
  SELECT COUNT(*) AS total_orders FROM WAREHOUSE.SALES_DIM_ORDER_BASE;

  -- Just Seller Cloud orders
  SELECT COUNT(*) AS sc_orders FROM WAREHOUSE.SALES_DIM_ORDER_BASE WHERE ORDER_ID LIKE 'SC_%';

  If total orders is significantly higher than the old 622K (because SC now has full prod data), that's further confirmation — total order volume grew, Amazon "share" shrunk because more are     
  properly attributed to SC.

  Run those and share the outputs. If overlap + amazon_only ≈ amazon_distinct_orders, we're done.
