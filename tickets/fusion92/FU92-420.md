through **five revisions**; v1–v4 were each wrong in a different way and every correction came from

## The v5 answer — measure the FUNCTION, not the folder

The v4 headline ("essentially no real usage") was **rejected by Lori on internal review, and she was
right.** The counts were correct; the *sentence* was wrong, because the unit was wrong. Counting
audience folders answers "how much was produced", not "is anyone using this".

The service does three things. Only one is being used.

| Function | Endpoint | Count | Period |
|---|---|---|---|
| **LOOK** — what audiences does this project hold? | `GET /projects/{p}/audiences` | **10,987** (~83/working day, 44+ distinct projects) | 2026-02-10 → 08-10 |
| **CONVERT** — turn an audience into platform files | `POST /audience/upload` | **5** | same |
| **RELEASE** — copy files to the production area | `POST /audience/process` | **3** | same |

**Roughly 2,000 reads per conversion.** All three come off one instrument over one period in one
unit, so they *are* comparable with each other — and are **not** comparable with the folder counts.

**The short version: their team is in this tool every working day. Nobody is converting.**

### The instrument, and why it is trustworthy

`Connected to Nextcloud!` is emitted once per request by `create_file_handler()` — a per-request
counter, not a session or startup line. 10,987 requests across two container logs (10,153 + 834).
**Calibrated** against a fully independent Nginx proxy log: **exact agreement on 21 of 22
overlapping days.**

- **Reads are human-driven, machine-proxied.** Zero calls on all four Saturdays; 97% inside working
  hours; inter-arrival CV **8.2** (a poller is ~0). The UA is `node` from Azure — the DIOS backend —
  so **no per-user attribution is possible from our side.**
- **Empty-reply share is 99.5% (1,596 of 1,604)** — measured on the **proxy log only, 13 Jul–10 Aug**,
  because that is the only record of response *bodies* and it retains ~4 weeks. It is **NOT** a share
  of the 10,987. Every reply was a successful HTTP 200 containing `[]`; nothing failed.
- **The arrow runs one way.** Converting is what *puts* an audience in the holding area; looking only
  *reports* what is there. So an empty list is the **result** of nobody converting, not the cause.
  The backwards reading — "our tool showed them nothing so they couldn't proceed" — would make this
  our defect. It isn't. The list is a mirror, not a gate.

application lines at all). Correcting for re-runs **strengthens** the campaign conclusion — the
demonstrable re-runs sit in test/debug bursts, so it inflates the *test* count.

**Three definitions of "real", published with their overlap** rather than collapsed into one number:
campaign-named **26** · NetSuite-numbered **38** · both **7** · both-admitting-repeated-digits **13**.

### Two findings that read like faults and are not

- **Mar–Jul 2026 is a REAL zero**, not an outage — the service served 1,590–2,155 requests/month
  through it. [[DV-329]]'s outage was brief. Do **not** report that window as service-down.
- **Single environment, proven three ways.** All four `dios-api` containers ever created share
  `NEXTCLOUD_HOST=nextcloud.fusion92.net`, `PATH=DAX`, `STAGING_PATH=DAX_RAW_DoNotUse`; 44,576 log
  lines never name another host; all 10,689 requests hit one address. A 100-folder nested-copy gap
  was tested — **0 of 100 new**.

## Withdrawn in v5 — and why

- **The warehouse figure was void.** v2–v4 leaned on `DIOS_AUDIENCE_NAME` being empty across all
  **14,709** flight records. The app writes `audience_name` (`flight_metadata.json:907`); the sync
  model declares `dios_audience_name` and no `audience_name`
  (`workflows/.../dax_api/jobs/schema.py:266,274`); `ConfigDict` has no `extra="allow"`, so Pydantic
  **drops the unknown key**. That column could *never* have been non-zero — and was created
  2025-12-03, six weeks *after* the last campaign conversion. A ~1-line `validation_alias` fixes it;
  the same file already does exactly that for `media_payer` at `:287`. **NOT TICKETED.**
- **The whole FU92-336 / December section.** It over-read *one* client comparison test into a
  standing parallel workflow, and the dates run backwards (their message was December; campaign
  conversions stopped in October). **Consequence:** the `_all` flat folders revert to **producer not
  established** — only that message identified them as the client's. 5 folders, 146 files,
  2026-02-26 → 2026-05-18, in a layout this service has no code to produce on any ref.

## Traps — read before re-analysing this data

- **`list_folders()` / `get_folder()` is create-or-get.** It *creates* the folder it is asked about
  (`nextcloud/api_wrappers/webdav.py:630`). Use `get_file()` for existence checks. This was the
  original defect (PR #2, fixed) **and** it later recreated folders a *cleanup verification* had just
  deleted. Verify a deletion by `PROPFIND` on the **parent**, never by listing the child.
- **Folder existence is not a usage signal** — two independent causes: the create-on-read defect, and
  QA traffic. [[flight-check]] runs prod and QA against a single `DIOS_API_URL`, so with one DIOS
  deployment **QA activity writes into production storage.** Test names in prod storage are expected.
- **Do NOT filter on project folder alone** — that was the v1/v3 error and it discarded real work
  filed under ad-hoc names. Classify on audience content. `PRJ777777` / `PRJ333333` / `PRJ898989`
  match `PRJ\d{6}` but are placeholders.
- **`DAX/` contains a nested copy of the staging tree.** Excluding it takes activation 257 → 37.
- **Container logs are an incomplete usage record.** The 2025 image's docker timestamps are stdout
  **FLUSH** times, lagging up to 32 days — unusable; use the embedded epoch in `timer start`.
- **"The cleanroom" is AMBIGUOUS at Fusion92 — never write it unqualified to Dave.** The **Viant
  Cleanroom** is the documented downstream route ([[fusion92-data-architecture]]); separately,
  **Snowflake Clean Rooms is an initiative Dave himself owns** ([[fusion92]]). Client PDF names Viant
  explicitly.
- **`grep` into a PDF proves nothing** — font subsetting defeats it. Scan
  `docs/evidence/report.filled.html` (the exact text the PDF renders), or extract with `pdftotext`,
  which decodes the content streams properly.
- **Chrome headless needs ABSOLUTE paths** for `--print-to-pdf`. A relative path fails silently and
  leaves a **stale** PDF beside fresh CSVs.

## Lessons that generalise beyond this ticket

1. **The unit is the answer.** Four revisions counted the right things and answered the wrong
   question. Before counting, ask what *one unit of the thing being asked about* is — here, a
   request, not a folder.
2. **A count is not a sentence.** 114 conversions and "essentially no real usage" are different
   claims; the data supported the first and not the second.
3. **Publish overlapping definitions with their overlap.** Three live definitions of "real" (33/38/8
   in v4, intersecting on 15) were used interchangeably in prose. Now: all three, plus the overlap.
4. **Removing prose does not remove its generated footnotes.** Cutting the FU92-336 section left
   three generated `client_footnote` strings still asserting its claim *and* pointing at "the section
   above" — in the **shipped PDF**, contradicting another footnote on the same page. Found
   2026-08-10 during a grounding sweep, after the pack had gone to Lori. **When a section is cut,
   grep the generator for every string that referenced it.** The internal `basis` fields were already
   correct; only the client-facing wording was stale, which is exactly why nobody noticed.
5. **The build enforces what it can; it cannot tell you the basis is honest.** `docs/evidence/CLIENT-DELIVERABLE-CHECKLIST.md`
   lists the six checks this deliverable has actually failed, and which assertions gate which.
