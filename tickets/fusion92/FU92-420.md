# FU92-420 — DIOS API Usage Visibility

**Status:** Delivered to client, awaiting Fusion92 response
**Jira:** https://analyticlabsdc.atlassian.net/browse/FU92-420
**Branch:** `FU92-420-usage-visibility` in [[custom-fusion-92-audience-api]] (pushed, unmerged — evidence only)

## The ask

Dave Nugent (Fusion92), relayed by Lori Beck: *"is there a way we can tell how many calls or
usages or files, to give him some awareness of system usage?"* The underlying question was whether
the media team uses the audience→platform conversion feature, or prepares platform files by hand.

## The answer (v2 — revised 2026-07-28 after client pushback)

Measured by **full enumeration** of the audience storage — 246 project folders, 377 audience
folders. **Counting basis: per-platform output subfolders**, which only a real conversion creates.
Never folder existence (see § Traps).

### Classification — by audience content, not project folder

Project naming was undisciplined, so a folder-name filter discards real work. Hand-audited across
all 114 conversions.

| Classification | Count |
|---|---|
| Real audience, numbered NetSuite project | **8** |
| Real audience, ad-hoc project folder (`manual_1`, `AP_1`, `PRJ_Alex HH`, `PRJ33333`…) | **25** |
| Testing / QA / scratch | **81** |
| **Total** | **114** |

**Real total 33**, spanning 2025-05-15 → 2025-11-03. Real work per month:
May 1 · Jun 5 · Jul 0 · Aug 1 · **Sep 10** · **Oct 15** · Nov 1 · then none.

### Dave's three questions, answered

| Question | Answer |
|---|---|
| Are they using it? | **Yes — modestly, and not recently.** 33 real audiences, none since 2025-11-03 |
| How many calls / usages / files? | **1,582 platform-ready output sets** (462 from real audiences) |
| Or doing it by hand? | **Both.** File prep fully automated; release step used **0 times** for real audiences |

**Strongest finding:** the tool built the platform files and the team took over manually from there.
That also explains the reporting gap — the tracked part of the workflow ends where the manual part
begins.

### Production timeline — verified from registry and container history

- Images `1.2`–`1.7` built Apr–May 2025; container `dios-api-1.7` created **2025-05-20**, ran nine
  months. **The service was live from May, not fall.**
- Codebase consolidated into the repo **2025-09-05** (*"Add most recent DIOS API code to the repo"*),
  and real audience work begins **2025-09-02** — the same week. The May build then ran unchanged for
  eight months.

So the client's "finalised for production in the autumn" holds, for a better reason than given.

### Other findings

- **Reliability 98%** — 112 of 114 produced complete output across all 14 platforms. The last real
  audience job ran cleanly, so nothing suggests the tool stopped working.
- **Nothing real was ever released.** Last release of any kind 2025-05-30 — ten days after go-live,
  months before the Sep–Oct work. The 12 audiences in both staging and production are all tests.
- `DIOS_AUDIENCE_NAME` empty across all **14,709** flight records.

### Method decision worth keeping

**No date cut-off was applied.** Any cut-off chooses a date and the date shapes the story — which
invites exactly the challenge the client raised. The full timeline is reported with the production
era annotated, and the classification tables shown so the client sees the judgement rather than
trusting it.

## Two defects found, fixed and deployed

Production now runs `ghcr.io/aldc-io/dios-api:FU92-420` (`main@39aeb01`, `sha256:6576cd4d…`).

**1. `list_files` created the folder it was asked to list** (PR #2, merged). `get_folder()` is
create-or-get per its own docstring (`nextcloud/api_wrappers/webdav.py:630`), so
`GET /projects/{p}/audiences` created a folder for every name passed to it — including from the
audience-name dropdown in ordinary UI use. Now uses `get_file()`.

**2. The image was shipping a credential and personal data** (PR #3, merged). `dockerignore` was
misnamed (no leading dot) so Docker never read it, and the Dockerfile does `COPY . .`. Every prior
image therefore contained `client/client.py` (plaintext production API key, line 16) and
`client/DIOS payload from Brian 2024-01-13.json` — audience rows with names, postal addresses,
email, IP and phone. Verified absent from the running image.

> **Still open:** the committed payload sample remains in git history. Removing it needs a rewrite
> — deserves its own ticket.

## Traps — read before re-analysing this data

- **Folder existence is not a usage signal.** Two independent causes: the create-on-read defect
  above, *and* QA traffic (below).
- **Test project names in production storage are expected.** [[entities/repos/flight-check|flight-check]]
  runs prod (`dax.fusion92.eclipse.aldc.io`) and QA (`dax.fusion92.eclipse.aldc-ca-w1.com`), both
  proxying DIOS through a single `DIOS_API_URL`. With only one DIOS deployment they address the
  same instance, so **QA activity writes into production storage.**
- **`PRJ777777` / `PRJ333333` / `PRJ898989` match `PRJ\d{6}`** but are placeholders. Excluding
  project numbers drawn from ≤2 distinct digits matters. But do NOT filter on project folder alone —
  that was the v1 error, and it discarded 25 real audiences processed under ad-hoc folders. Classify
  on audience content.
- **`DAX/` contains a nested copy of the staging tree.** Excluding it takes activation from a bogus
  257 to the real 37.
- **Container logs are an incomplete usage record** — detailed upload logging exists only in the
  newer image, and ~20% of days (mostly weekends) carry no entries.
- **"The cleanroom" is AMBIGUOUS at Fusion92 — never write it unqualified to Dave Nugent.** There are
  two. The **Viant Cleanroom** is the documented downstream activation route
  (`DIOS → Manual Upload → Nextcloud → Viant Cleanroom → DAX Activation → DSP`,
  [[fusion92-data-architecture]], from client Confluence CF92/1382088715, labelled *"Temporary State
  Flow"* — so its currency is unverified). Separately, **Snowflake Clean Rooms for F92 + clients
  (e.g. Experian) is an initiative Dave himself owns** ([[fusion92]]). A document addressed to him
  saying "straight into the cleanroom" reads as *his* Snowflake initiative. Client PDF corrected to
  name Viant explicitly (`ac2d596`).
- **The recorded 90-day Nextcloud retention is not observed for folders** — see
  [[fusion92-data-architecture]]. Doesn't affect these figures (basis = platform subfolders, which
  persist), but a real purge would have understated every count, so don't lean on that line.
- **Low volume matches the documented maturity.** Phase 1 was quick-delivery with Fusion92 running
  campaigns manually; the integration is logged as *"paused 2–3 weeks (client priorities)"* in
  [[fusion92-data-architecture]]. A pilot that never scaled — not missing data.

## Method note

The count went **5 → 10 → 114 → (33 real of 114)** across four attempts. The first three wrong
answers came from the same error — **sampling and generalising.** The fourth came from the mirror
image: a *filter* that was too strict, requiring a numbered project folder and so discarding real
work processed under ad-hoc names. Client pushback caught it. An empty Snowflake column read as "unused"; eleven guessed project
names returning `[]` read as "zero usage"; one grep anchor read as "the log is complete". What
fixed it was enumerating the population and corroborating logs against stored artifacts. The
first answer would have told the client the opposite of the truth.
