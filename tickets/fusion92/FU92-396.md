# FU92-396 — DAX Manual Metrics Blocked by Stale JWT Role

Ken Kocna's JWT session token carried stale `user` role after being updated to `buyer` in CosmosDB. The `disabled_if` condition on Manual Metrics Input blocks `user` role on submitted/approved statuses, causing "Entry unavailable due to flight status or user role."

## Status

**Deployed + verified in production** — 2026-05-07. [PR #35](https://github.com/ALDC-io/flight-check/pull/35) merged, deployed via Azure App Service workflow dispatch, slot-swapped to production. End-to-end validated. Jira status: Ready for Customer.

### Production Validation (2026-05-07)

1. Changed test user role to `user` in CosmosDB → logged in → confirmed "Entry unavailable" error on Approved flight (bug reproduced)
2. Changed role to `buyer` in CosmosDB **without logging out**
3. Waited for 5-minute JWT refresh cycle
4. Confirmed via `/api/auth/session` that role updated from `user` to `buyer` automatically
5. Refreshed flight page → Manual Metrics Input table unlocked and editable
6. Confirmed via Azure log stream that `[authOptions] Role refresh` entries fired correctly

## Root Cause

The JWT callback in `authOptions.ts` only copied user roles from the initial login token and never re-fetched from CosmosDB. The parent Eclipse portal mints the JWT at login time — so even logout/login cycles didn't pick up the updated role because the portal's token also carried the stale value.

### The condition chain

The `f92_metrics_table` field in `metadata/job_details.json` (lines 302–327) has two `disabled_if` conditions (OR logic):

| Condition | Status trigger | Role gate | Effect |
|---|---|---|---|
| 1 | Submitted, Change Submitted, Change Requested, Change Approved, Approved | scope: includes, types: ["user"] | Disabled only for `user` role |
| 2 | In Review, Change In Review | scope: excludes, types: [] | Disabled for all roles |

With Ken's stale JWT carrying `user` → Condition 1 fires → metrics table disabled.
With correct `buyer` role → Condition 1 does NOT fire → metrics table editable.

## Fix

Added periodic role refresh to the JWT callback in `authOptions.ts`:

- `fetchFreshUserData()` calls the existing `user/list` v1 core API endpoint server-side
- Refreshes `applications` and `groups` every 5 minutes (`ROLE_REFRESH_MS`)
- Fails gracefully — if the API call fails, existing token data is preserved unchanged
- Added `roleRefreshedAt` to JWT type definition in `types/next-auth.d.tsx`

### Files changed

| File | Change |
|---|---|
| `authOptions.ts` | `fetchFreshUserData()` + periodic refresh in `jwt` callback |
| `types/next-auth.d.tsx` | Added `roleRefreshedAt: number` to JWT interface |
| `__test__/fu92-396-condition.test.ts` | 5 tests proving `buyer` unlocks metrics, `user` is blocked |

## Evidence

5 passing Jest tests (`__test__/fu92-396-condition.test.ts`) using the exact `disabled_if` config from production metadata:

- `user` + "Change Submitted" → BLOCKED (the bug)
- `buyer` + "Change Submitted" → ALLOWED (after fix)
- `buyer` + "Approved" → ALLOWED
- All roles + "In Review" → BLOCKED (by design)
- `buyer` + "Draft" → ALLOWED

## Broader Impact

This is a systemic fix. Any future role changes for any DAX user will take effect within 5 minutes of the next page load, without requiring manual intervention or cache clearing.
