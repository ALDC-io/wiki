# GP-266 — Previous Period / LY on the widget (Ad Item from Airtable)

Surface a **previous-period and last-year (LY / year-over-year)** comparison on the SKU Profitability dashboard widgets. Jira summary is "Ad Item from Airtable — additional details needed before moving forward" (status **To Do → In Progress**, High, Paul). The original ask referenced sourcing the figure "from Airtable."

> **Design decision (2026-06-18): use the YoY the app already computes — do NOT source LY from Airtable.** Implemented as an additive inline badge on `MetricCard`. PR open, merge pending a staging screenshot. See [[concept-gep-data]].

## The key finding

The [[concept-gep-data]] app **already computes** both previous-period and year-over-year, identically, via date-shifted Eclipse `dataset/request` queries (`getPreviousPeriodDateRange()` / `getYearOverYearDateRange()` in `src/lib/utils.ts`; fired as parallel `fetchMetrics()` calls in `src/hooks/useMetrics.ts`). The values (`previousValue`/`change`, `yearOverYearValue`/`yearOverYearChange`) are attached to every `MetricCardData` — but **previous-period is shown inline on the card face while YoY was tooltip-only**. So "LY on the widget" was a *display* gap, not a data gap.

## Why NOT Airtable (single-source-of-truth)

Sourcing **last-year actuals** from Airtable would be an anti-pattern:
- It duplicates data already held authoritatively in the PBI "Data Model" (13 years of Date dim) → drift/reconciliation risk.
- It adds a permanent manual-maintenance burden.
- A static Airtable figure would **not track the dashboard's timeframe/filter slicers**, so the comparison wouldn't move with the view — every other "similar date range" comparison here is a date-shifted query off `'Date'[Date]`. Airtable breaks that pattern.

**Airtable is only the right source if the figure is a manually-set Target/Plan that genuinely isn't in the warehouse** — and even then it should be ingested via the supplement pattern (Airtable → Snowflake → PBI model, like the Forecast CSV → `SALES_FCT_BUDGET`; the `AirtableV2` connector already exists in `eclipse_exp`), **not** a live frontend fetch. Open confirm with the client: do they want LY *actuals* (we have those) or a *Target* they maintain?
