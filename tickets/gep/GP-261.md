## 2026-06-10 (session 2) — Dashboard semantics validated by reverse-engineering the mockup; ASIN-count floor

**Consumer decided:** PBI Test Data Model (consistent with Navira marketing GP-225/226/277), potentially surfaced in **Eclipse 2.1** Liquid App. The `REPORT_COMMON` views serve both surfaces unchanged — Eclipse would read the same model. See [[project_analytics_stack]].

**`REPORT_COMMON.NAVIRA_MAP_VIOLATORS_OVERVIEW` rebuilt** with three evidence-gated semantics (all deployed to non-prod, no-regression proven — 787 sellers identical, headline `PCT_TIMES_MAP_VIOLATORS` unchanged for every seller):
- `SELLING_FBA` = ANY=TRUE (`MAX`) — dominant-brand pick was arbitrary for only 35/787 sellers whose flag disagrees.
- Per-day averages: denominator = `COUNT(DISTINCT CAPTURE_DATE)`, not the (date×brand) observation count — identical for 643/787 single-row-per-day sellers, but per-observation badly understated multi-brand sellers (e.g. 4.76 vs 165.67 avg ASINs).
- Raw additive measures + `BRANDS_90D`/`CAPTURE_DAYS_90D`/`OBSERVATIONS_90D` exposed so a PBI/Eclipse consumer can filter & sort without a redeploy. Computed straight from windowed history (reconciles to a rollup of the seller×brand fact) so seller-level `CAPTURE_DAYS` (a distinct count, non-additive) is correct.

**The "everyone's a 100% violator" problem — root-caused and fixed.** It was a metric/presentation issue, not a population one. Key findings from the data:
- `TOTAL_APPEARANCES` is a **daily price-check count (stock-like)**, an order of magnitude larger than the catalog (e.g. 389 ASINs listed vs ~4,200 appearances/day). Summing it over 90d inflates absolute volume; the **ratio** `viol/appr` survives because both sides inflate equally.
- **431 of 787 sellers (55%) had zero violations in the trailing 90 days.** Of the rest, the 92 sellers stuck at exactly 100% are **single-ASIN sellers** (avg **1.5 ASINs**) with one perpetually-mispriced item — noise. Real businesses average **11.7 ASINs**.
- **Reverse-engineered Justin's mockup against live data** (`screenshots/MAPS_Violator_Visual_data_structure_module_navira_snowflake_data_share.png`). The mockup's seller IDs are placeholders, but its exact column headers + dummy magnitudes (9–32% rate, 150–300 ASINs listed, 7–31 violating) confirm all three column formulas. Ranking real sellers by volume reproduces the mockup exactly — named businesses (Amazon, Sweetwater Sound, Whole9yards) land at mid-range % with hundreds of ASINs.

**Floor swapped from appearances to catalog size.** The min-appearances floor (N≥10) was the wrong lever — the noise has ~1,100 appearances but only 1.5 ASINs. Replaced with `MEETS_MIN_ASINS_LISTED` = **avg ASINs/day ≥ 3**: drops 83 of the 92 always-100% sellers while keeping every mockup-shaped real business (289 sellers survive; the 9 remaining 100% sellers have ≥3-ASIN catalogs all mispriced — legitimate worst offenders). Threshold is tunable in the BI layer. Worst-violators ranking = `PCT DESC, SUM_APPEARANCES_90D DESC`.

## Revised Decision (2026-06-01) — Native Secure Data Share + Local Materialization

> **Supersedes the 2026-05-25 Prefect decision below.** Prefect was shelved org-wide (2026-05-28, see [[project_prefect_shelved]] / [[prefect]]), which removed Option C. Re-evaluated the remaining options and selected **Option B: native Snowflake Secure Data Share + scheduled local materialization**, explicitly hardened to address the share failure modes that drove the original Prefect choice.

**Why Option B is now correct (and the failure modes are mitigated, not ignored):**

| Original objection to shares | How the hardened design answers it |
|---|---|
| 42-day frozen share went undetected (Sellercloud staleness) | Watchdog task compares row count + `HASH_AGG` content hash run-over-run; a frozen source raises a staleness alert |
| `CREATE OR REPLACE TABLE` silently drops share grants | That was on ALDC's **provider** side; here ALDC is the **consumer**. Watchdog still probes share availability (`SHOW SHARES` + `SELECT 1` in a TRY block) and alerts if the inbound share disappears |
| Cross-database grant loss caused a 14h outage | `REFERENCE_USAGE` requirement for multi-DB views is called out explicitly in the Justin guide; single-DB views are unaffected |
| Pure share = no data if share drops | **Local materialization** layer: reports read our own snapshot, never the live share — a dropped share degrades to *stale-but-available*, never broken |

**Why not Prefect anymore:** shelved org-wide; new connectors use Eclipse. A native share is also lower-maintenance than an ETL flow for Snowflake → Snowflake (zero-copy, zero compute, no credentials/egress).

### Target architecture (3 layers)

```
NAVIRA_SHARE (imported DB, live read-only)         ← never read by reports
        │  scheduled serverless TASK (full-snapshot CTAS; incremental MERGE only if a view exposes key + change column)
        ▼
{ENV}_DG1_GEP.NAVIRA_RAW (our own physical tables) ← durable, survives a share drop; retains prior snapshot
        ▼
WAREHOUSE_SOURCE views → existing warehouse pipeline ← read only from NAVIRA_RAW
```

- **Mitigation (stale-but-available):** `NAVIRA_RAW` is the durable copy; reports keep serving the last good snapshot, labelled with a `data_as_of` timestamp.
- **Detection:** `OPS.SHARE_SYNC_HEALTH` log table + an hourly watchdog task → `SYSTEM$SEND_EMAIL` (notification integration) + optional Slack/Teams webhook, surfaced on the Launchpad ops dashboard. Three checks: share-down (probe error / not in `SHOW SHARES`), staleness (last good sync older than 2× cadence), source-frozen (row count drop or unchanged content hash).
- **Derived views like `MAPS_VIOLATOR`** likely have no stable change key → default to full-snapshot CTAS each cycle with prior-snapshot retention.
