# GP-208 — Inventory Feed Ingestion & Modelling

Greenfield inventory fact table for [[GEP]]. Navira/GEP delivers a pre-aggregated inventory snapshot (CSV or data share) covering FBA availability buckets, GEP2 quantities, AWD measures, and kit quantities. The goal is to make this feed queryable inside the managed [[Snowflake]] environment at `PROD_DG1_GEP`.

## Status

- Discovery and design complete
- Client questions drafted and sent (see below)
- **Blocked on**: client responses to data source, grain, and delivery mechanism questions

## Key Decision: Data Source

The core question driving everything: **is the new feed from the same systems the old model used, or is it a new external source?**

| Path | When | Ingestion | Notes |
|------|------|-----------|-------|
| **A — Data Share** | New external source | Snowflake data share into `PROD_DG1_GEP.GEP_INVENTORY.*` | Preferred. Needs GEP account ID, table name, refresh cadence, timezone |
| **B — File Stage** | Data share not ready | CSV drop → `COPY INTO` with validation | Stopgap. Needs delivery schedule, row count checksums |
| **C — Existing Pipelines** | Same source as old model | Build view on `SELLERCLOUD_SQL.*` + `AMAZON.*` tables | Must confirm pipelines still refreshing. Coverage gap: AWD, CA FBA, kits have no upstream source |

## Architecture

```
Layer 1: Raw Ingestion (Path A/B/C)
   ↓
Layer 2: WAREHOUSE_SOURCE.INVENTORY_FCT_BALANCE (secure view — transform + snake_case + derived fields)
   ↓
Layer 3: WAREHOUSE.INVENTORY_FCT_BALANCE (append-only materialized table + scheduled task)
   ↓
Layer 4: extract_inventory_current.sql (latest snapshot + product dim join)
```

### Recommended approach
- **Append-only** physical table (retains all history)
- `extract_inventory_current.sql` filters to `MAX(CAPTURE_TIMESTAMP)` for latest snapshot
- Avoids retool if GEP later wants trend/DOH analysis

## Grain Decision (Go/No-Go Gate)

Do not build Layer 2/3 until confirmed:

| Option | Grain | Implication |
|--------|-------|-------------|
| A | MASTER_SKU x CaptureDate | One snapshot per SKU per day; Iteration is metadata |
| B | MASTER_SKU x Iteration | One snapshot per SKU per batch; multiple rows/day possible |

**Recommendation**: Option A with hybrid design — append-only table, current-snapshot extract view.

## Client Questions (Sent)

1. **Data source** — Same systems (Sellercloud + Amazon) or new external feed?
2. **Delivery mechanism** — Data share preferred. Need account ID, table, cadence, timezone
3. **Iteration field** — Batch counter? Planning cycle? Can there be >1/day?
4. **Column definitions** — AWD meaning, kit column lifecycle, FBA total vs detail breakdown, CA FBA population timeline, negative reserved values
5. **Historical data** — Full history recommended; confirm client wants this
6. **Priority use cases** — DOH, stock-out detection, AWD replenishment?
7. **On-order quantities** — Use feed value directly or join from purchasing fact?

## QA Checklist

- Row count: source vs fact must match exactly
- MASTER_SKU join rate: alert if < 95% match to `SHARED_DIM_PRODUCT`
- Null rate: 0 for mandatory fields (MASTER_SKU, BALANCE_DATE, ITERATION)
- Negative values: log reserved column negatives, don't reject until policy confirmed
- Duplicates: zero tolerance on MASTER_SKU + CAPTURE_TIMESTAMP
- Day-over-day delta: alert if > 50% swing per SKU
- Cross-validation: compare to old `inventory_fct_balance` for overlapping columns
- Out-of-order loads: insert as valid history, flag `IS_OUT_OF_ORDER = TRUE`
