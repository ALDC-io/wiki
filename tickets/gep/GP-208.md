## TEST Deploy Findings (2026-04-16)

The TEST deploy surfaced two code issues and one upstream infrastructure issue. Both code issues were fixed; the infrastructure issue is out of scope.

### Code fix 1 — Amazon FBA CTE was picking stale per-SKU rows

**Symptom**: After deploying the fact, `SELECT MIN(BALANCE_DATE), MAX(BALANCE_DATE) FROM WAREHOUSE.INVENTORY_FCT_BALANCE` showed dates spanning 2024-08-11 → 2026-04-16. "Current snapshot" fact should only contain today's dates.

**Root cause**: The AMAZON_FBA CTE used `QUALIFY ROW_NUMBER() OVER (PARTITION BY SKU ORDER BY ___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___ DESC) = 1` — this picks the latest capture *per SKU*, which retains rows for SKUs that dropped out of the FBA report months ago. Their "latest" was 2024-08-11 or similar.

**Fix**: Pin to the latest global batch instead of per-SKU latest:

```sql
WHERE ___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___ = (
    SELECT MAX(___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___)
    FROM PROD_DG1_GEP.AMAZON.CURRENT_REPORT_FBA_INVENTORY
)
-- Secondary dedup for rare same-batch SKU dupes
QUALIFY ROW_NUMBER() OVER (PARTITION BY SKU ORDER BY SKU) = 1
```

This aligns with Phase 2's future `CAPTURE_TIMESTAMP`-pinned append-only logic. Row count dropped from 7,470 → 3,510 post-fix, which is the correct count for "latest-batch FBA unioned with latest-date Sellercloud."

**Related concept**: [[accumulating-source-tables]] — this is the same class of issue documented there, but the fix there (latest-per-key) only works for *history* facts. Current-snapshot facts need latest-global-batch. Consider updating that page to distinguish the two patterns.

### Code fix 2 — Extract's MAX(BALANCE_DATE) filter silently hid Sellercloud rows

**Symptom**: After the fact rebuild to 3,510 rows, the extract returned only 388 rows. Filter `WHERE FCT.BALANCE_DATE = (SELECT MAX(BALANCE_DATE) FROM WAREHOUSE.INVENTORY_FCT_BALANCE)` was dropping any rows where BALANCE_DATE ≠ MAX — in Phase 1 this is a silent data loss whenever any source lags.

**Root cause**: The MAX-date filter was designed for Phase 2 (append-only history, where "current" means "latest captured snapshot"). In Phase 1, the fact is already current-snapshot by construction (one row per PRODUCT_ID at its source's latest capture). BALANCE_DATE varies per row depending on which source contributed — FBA rows have today's date, Sellercloud rows have 2026-03-04. Filtering by global MAX throws away the Sellercloud rows.

**Fix**: Remove the `WHERE` clause entirely in Phase 1. Re-introduce it in Phase 2, but pin by `CAPTURE_TIMESTAMP` not `BALANCE_DATE`.

## Phased Approach

**Phase 1 — Current snapshot (in progress)**
- Grain: `PRODUCT_ID × BALANCE_DATE`, one row per product, latest snapshot only
- `WAREHOUSE.INVENTORY_FCT_BALANCE` refreshed via full replace (`CREATE OR REPLACE TABLE AS SELECT`)
- Simplest implementation; validates column set and joins against the prior model first
- Ship and QA before adding history

**Phase 2 — Append-only history (future)**
- Switch the table's scheduled task to `INSERT ... WHERE CAPTURE_TIMESTAMP > MAX(existing)`
- Table accumulates forward from Phase 2 cutover date (Sellercloud has no upstream history to backfill)
- `extract_inventory_current.sql` already filters to `MAX(BALANCE_DATE)` — switch is transparent to consumers

## Moving-Target Source Tables — Design / Build / Test Implication

See [[accumulating-source-tables]] for the generalized pattern and QA workflow. Below is the specific finding from this ticket.

**Finding (2026-04-16, Phase 1 QA):** `PROD_DG1_GEP.AMAZON.CURRENT_REPORT_FBA_INVENTORY` accumulates multiple timestamped versions of each SKU — it is not a single-snapshot table despite the `CURRENT_` prefix. `___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___` distinguishes batches; the same SKU can appear multiple times across batches.

Our Phase 1 view resolves this by picking the latest per SKU at **query time** (not pinned to a snapshot):

```sql
QUALIFY ROW_NUMBER() OVER (PARTITION BY SKU ORDER BY ___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___ DESC) = 1
```

### What this means for testing

A CTAS built at time T and a direct reconciliation query run at time T+N will disagree if the source ingested new batches between T and T+N. During QA we observed:

- **8-hour gap** between CTAS and re-reconciliation → 0.8% drift across FBA measures, with directional signs matching real inventory flow (working↓, shipped↑, available↑, reserved↑)
- **0-second gap** (rebuilt and immediately queried) → 0.18% drift remained, ~1 SKU and ~585 units across 316K, attributable to non-deterministic tie-breaking inside same-timestamp batches

**Practical test tolerance**: ≤1% unit delta, ≤5 SKU delta is acceptable for Phase 1. Beyond that indicates a real bug.

### What this means for design

- Phase 1's "latest at query time" is correct for a current-snapshot fact and cheap to build, but makes deterministic reconciliation impossible — don't block on 100% match
- Phase 2 append-only ingests each new `___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___` batch on arrival; rows are frozen once written. Reconciliation becomes bit-exact because the fact pins to a specific capture timestamp rather than recomputing "latest"
- The accumulating source table is a **gift** for Phase 2 — we don't need to stand up a new history mechanism; we read history from the existing table using `WHERE ___ALDC___GLOBAL_HISTORY_TIMESTAMP_START___ > (SELECT MAX(CAPTURE_TIMESTAMP) FROM fact)`

### Build/test runbook addition

- Always run the **timestamp-drift diagnostic (Q7a)** before interpreting reconciliation output
- Rebuild the CTAS and run reconciliation **in the same worksheet session, back-to-back**, to minimize drift
- Flag any drift > 60 seconds in the diagnostic before drawing conclusions from measure totals

## Sample Feed Reference (Iteration 46, 2026-03-24)

GEP shared a 100-row sample (`GEP/_testing/GP-208/sample_inventory_data.csv`, gitignored). Full analysis in `GEP/_testing/GP-208/sample_analysis.md`. Key takeaways:

- Feed is `MASTER_SKU × CaptureDate` — matches our grain (PRODUCT_ID resolves to MASTER_SKU via `SHARED_DIM_PRODUCT`)
- Reverse-engineered aggregates:
  - `Total US FBA Available` = `US FBA Available` + `US FBA Rsrvd Trnsfr` (transfer-reserved counts as available)
  - `Total US FBA InTransit` = sum of all Working + Shipped across US/Direct/SCC programs + `AWD InT`
  - `Total Non Sellable` = `Non Sellable Qty` + `US FBA Rsrvd Prcss` + `US FBA Rsrvd Orders`
- Reserved-column 3-way split (Orders / Prcss / Trnsfr) is **not in our raw Amazon report** — `AFN_RESERVED_QUANTITY` is a single lump. Sourcing the split requires Amazon SP-API Reserved Inventory Report (not currently ingested)
- `Direct FBA` and `SCC FBA` program columns are all zero in sample — likely unused; SCC ties to AWD
- AWD and CA FBA do populate for some rows (not just placeholders) — worth prioritizing if GEP asks
