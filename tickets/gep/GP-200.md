# GP-200 — Amazon UK Addition to Orders

End-to-end addition of Amazon UK order data into the [[GEP]] order pipeline. This was the first new-marketplace onboarding since the original US/CA/MX setup and served as a template for future marketplace additions. The ticket also produced a detailed deployment runbook that generalizes to any Snowflake/Power BI deploy.

## Problem / Request

[[GEP]] added Amazon UK to their Amazon marketplaces. Orders from `Amazon.co.uk` were not flowing into the warehouse because no [[Eclipse]] connection or template existed for UK Seller Central, and the four SQL files that reference `CURRENT_REPORT_ALL_ORDERS` only consumed the US/CA/MX table. Scope was orders-only; ad spend and traffic were out of scope.

## Design / Approach

### Eclipse layer (new connection + template)

| File | Action |
|---|---|
| `GEP/eclipse/connections/amazon_seller_central_uk.json` | Created. Cloned from US connection, replaced with UK credentials from Dashlane. |
| `GEP/eclipse/templates/amazon/all_orders_report_UK.json` | Created. Filter marketplace = `"gb"` (ISO code). Data lands in `CURRENT_REPORT_ALL_ORDERS_UK`. |

Both registered in CosmosDB (`work_connection` + `work_template` collections).

### SQL layer (UNION ALL pattern)

Introduced an `AMAZON_ALL_ORDERS` CTE in each file that UNIONs US and UK tables with explicit named columns (guards against schema drift):

| File | Change |
|---|---|
| `sales_dim_order_base.sql` | Added CTE to existing WITH block |
| `sales_fct_amazon_orderline.sql` | Added new WITH block + CTE |
| `sales_fct_seller_cloud_orderline.sql` | Prepended CTE to existing WITH |
| `extract_warehouse_metadata.sql` | Added UK metadata UNION ALL block |
| `shared_dim_marketplace.sql` | Added company 178 ("Amazon UK") to fallback VALUES |

### UK currency fix (discovered during QA)

**Problem**: The original design joined Amazon orders to `SHARED_DIM_COMPANY_CURRENCY_MAP` on `CURRENCY_NAME` to determine `COMPANY_ID`. UK orders with non-GBP or NULL currencies (Pan-European cross-border orders in EUR, SEK, etc.) were misattributed to Amazon US (company 163).

**Solution**: Filter the UK CTE leg with `WHERE SALES_CHANNEL = 'Amazon.co.uk'` and `COALESCE(CURRENCY, 'GBP')` for NULL rows. This excludes genuine European marketplace orders and ensures all true UK orders resolve to company 178.

- Added "Amazon UK" row to Marketplace Config CSV (with `APPLY_DISCOUNT_TO_NET` and `DTC_FEE_RATE` values)

## Implementation

Full deployment followed a 10-phase runbook (documented in source as `Order of Operations - Inception to Completion.md`):

1. **Pre-requisites**: UK credentials, `min_date` confirmation
2. **Register connection + template** in CosmosDB
3. **Run connector + validate ingestion** into `PROD_DG1_GEP.AMAZON.CURRENT_REPORT_ALL_ORDERS_UK`
4. **CSV supplements** updated on Nextcloud
5. **Local validation** in `WAREHOUSE_TEST_PAUL` schema
6. **Deploy SQL views** to Snowflake Test (order matters: dim first, then facts, then metadata)
7. **Materialize physical tables** via task chain (`TASK_WAREHOUSE_ORDERLINE_0`, 10-step DAG)
8. **End-to-end validation** in Snowflake Test
9. **PR-based promotion** to `GEP/user-testing`
10. **Power BI Test model** refresh + smoke test in Explore

## Pitfalls Encountered

These are the highest-value learnings from this deploy and are likely to recur:

### 1. Data-share gaps in Snowflake Test (can recur post-deploy)

SQL files reference `PROD_DG1_GEP.*` schemas via a manually configured data share. Missing objects only surface as errors when views/tasks try to compile. During GP-200, `CURRENT_MAIN_PURCHASEITEM` and `CURRENT_SPONSORED_PRODUCTS_ADVERTISED_PRODUCT_REPORT` were both missing at deploy time. Fix: add objects to the share in [[Snowflake]] prod UI. See also [[GP-207]].

**Important: this pitfall can recur post-deploy.** On 2026-04-21 the 06:00 PDT task chain succeeded with `CURRENT_REPORT_ALL_ORDERS_UK` present, the table dropped out of the share mid-day (most likely via an Eclipse `CREATE OR REPLACE TABLE` refresh cycle), and the 13:26 PDT task chain failed with the same missing-object error. A clean deploy does not mean the share stays clean. Full timeline and mitigation options tracked in [[GP-PENDING-data-share-stability]].

### 2. `extract_warehouse_metadata.sql` line 109 view-vs-table conflict

Line 109 creates a `SECURE VIEW` but the hourly task materializes the same name as a TABLE. Snowflake cannot replace a TABLE with a VIEW. The error is harmless; the next task run rebuilds the table from the updated source view. Long-term fix: change to `CREATE OR REPLACE TABLE`.

### 3. Data-share switch causes volume step-change

[[GP-207]]'s prod-to-test data share switch landed alongside GP-200. Post-deploy volumes were dramatically different from pre-deploy (25K AMZ orders + 2.52M SC orders vs 622K Amazon-only before). The AMZ count dropped because the dedup logic correctly reattributed orders to Seller Cloud with the full prod dataset. **No data was lost** -- it was reattributed. Always communicate step-changes to stakeholders.

### 4. Power BI relationship: Order is not directly related to Marketplace

`SALES_DIM_ORDER_BASE` does not have `MARKETPLACE_KEY`. Marketplace joins through orderline tables. Using `Order ID (Count)` against `Marketplace Name` in [[Power BI]] returns the same total for every marketplace. Fix: use measures from Marketplace Measures or columns from Order Line tables.

### 5. Missing EUR mapping in currency map

1 UK order surfaced as `ZZZ` (unmapped). SellerCloud currency code 3 = EUR was not in `SHARED_DIM_COMPANY_CURRENCY_MAP`. All European Amazon companies (France 181, Germany 182, Italy 184, Spain 187) also showed as `ZZZ`. Pre-existing gap exposed by the data-share switch. Tracked as a separate ticket.

### 6. Power BI sparse matrix misreading

Sparse matrices (Marketplace x Currency) are easy to visually misalign. Trust column totals in the Total row before trusting individual cells. Cross-check against Snowflake when in doubt.

## What "Done" Looks Like for the Customer

Reusable UAT checklist for any new-marketplace rollout. Send this (or a tailored version) to the customer or client success manager once the test PBI model is refreshed.

Ask the customer to open the **GEP Test Power BI model** and verify:

1. **New marketplace appears** in the marketplace slicer alongside the existing ones.
2. **Sales drilldown works** — use a **Marketplace Measure** (e.g. *Actual - Sales - Gross*) against **Marketplace Name**. Gotcha: a raw `Order ID` count against Marketplace Name will return identical totals for every marketplace because `SALES_DIM_ORDER_BASE` is not directly related to Marketplace. This is a PBI relationship quirk, not a data issue. See Pitfall 4.
3. **Currency attribution is clean** — new marketplace sales should be in the expected currency only (e.g. GBP for UK, no USD/EUR leakage).
4. **Date coverage is realistic** — orders span from the Eclipse template's `min_date` forward, not a single-day dump.
5. **Existing marketplaces are stable** — all previously-visible marketplaces (US/CA/MX) should look unchanged. The new marketplace is strictly additive.

Direct Snowflake validation in `TEST_DG1_GEP` if the customer prefers:

```sql
SELECT COUNT(*), MIN(CREATE_DATE), MAX(CREATE_DATE)
FROM WAREHOUSE.SALES_DIM_ORDER_BASE
WHERE COMPANY_ID = <expected_company_id>;
```

### Expectation-setting for test environment

Worth flagging up-front so the customer doesn't repeatedly ask "is this current?":

- **Raw Amazon pull** is continuous (Eclipse scans every 5 min, pulls daily-window partitions), so the raw table in prod refreshes throughout the day.
- **Test warehouse** rebuilds **once daily at 06:00 Pacific** via `TASK_WAREHOUSE_ORDERLINE_0`. Today's orders appear in the test warehouse the following morning.
- **Power BI test model refreshes once daily on a scheduled refresh** (configured on the semantic model in the GEP Test Models workspace). The test PBI model therefore lags Snowflake by up to a day in practice (warehouse rebuilds at 06:00 PDT, then the PBI scheduled refresh fires separately). For UAT or post-deploy customer validation, trigger an ad-hoc refresh so the test model reflects the deploy immediately rather than waiting for the next scheduled fire. See [[Power BI]] § Model Refresh for the procedure.

## Lessons Learned

1. **The UNION ALL CTE pattern is the right approach** for adding new marketplace data sources. Explicit named columns prevent schema drift between regional tables.
2. **Always filter by `SALES_CHANNEL`** when a regional Amazon table contains cross-border orders. Currency alone is insufficient for marketplace attribution.
3. **Deployment runbooks should be written during the first deploy**, not after. The GP-200 runbook (`Order of Operations`) became the reference for all subsequent [[GEP]] deploys.
4. **Data-share gaps are the most common deploy blocker.** Pre-flight the task chain by SELECT-ing from each `PROD_DG1_GEP.*` object the view chain references.
5. **Pre/post snapshot comparison is essential.** Without it, the volume step-change from GP-207's data-share switch would have appeared as a GP-200 regression.
