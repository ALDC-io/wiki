# GP-203 — Add Traffic for Canada

Added Canadian marketplace traffic data to the traffic fact and defended the per-marketplace grain during PR review.

## Status

Completed. Merged to `GEP/development`.

## Problem / Request

The `TRAFFIC_FCT_ACTIVITY` fact only contained Amazon US traffic data. [[GEP]] needed Amazon CA (Canada) traffic included so analysts could compare US vs CA page views, sessions, and ordered product sales side by side.

## Design / Approach

Extended the traffic fact to include Canadian marketplace data alongside US data. The grain was set at `(ACTIVITY_DATE, PRODUCT_ID, CHILD_ASIN, PARENT_ASIN, MARKETPLACE_KEY)` -- one row per product per day per marketplace.

### PR review: GROUP BY change (not applied)

A reviewer proposed collapsing the grain to `(ACTIVITY_DATE, PRODUCT_ID, CHILD_ASIN, PARENT_ASIN)` by removing `MARKETPLACE_KEY` from the GROUP BY and aggregating metrics across marketplaces. This was **not applied** because:

1. **Before aggregation**: The natural key `(date, product, child ASIN, parent ASIN, marketplace)` preserves per-marketplace visibility. A SKU sold in both US and CA on the same day produces two separate rows.
2. **After aggregation**: The natural key collapses, merging all marketplace metrics into a single row and requiring an arbitrary `MAX(MARKETPLACE_KEY)` -- destroying the ability to filter or slice by marketplace.
3. The upstream `SALES_AND_TRAFFIC_RAW` CTE already deduplicates via `ROW_NUMBER() ... QUALIFY` within each `(date, child ASIN, parent ASIN, currency)` slice, so the `LEFT JOIN MARKETPLACE_CURRENCY_MAP` does not create multiplicity.

## Implementation

Traffic fact was updated to include both US and CA data. The marketplace currency map stamps each row with its marketplace metadata via the existing join pattern.

## Testing / Validation

Confirmed US + CA data flowing with expected volumes:

| Marketplace | Row Count | Sum Sales |
|---|---|---|
| Amazon CA | 1,404,120 | $1,394,516.21 |
| Amazon US | 6,770,879 | $60,725,720.44 |

No unexpected marketplaces appeared. Per-marketplace grain preserved.

## Lessons Learned

1. **Defend the grain when reviewers suggest aggregation.** Collapsing marketplace out of the GROUP BY would have permanently lost per-marketplace detail at the fact level. Aggregation belongs in the reporting/BI layer, not the warehouse fact.
2. **Document why a PR suggestion was rejected.** Keeping the rationale on record prevents the same suggestion from recurring and helps future reviewers understand the design intent.
