# GP-283 — Navira: exclude order SC_8894973 from all numbers

Navira support request (Heather Tabor, 2026-06-11): "exclude this order from our numbers completely — 8894973". Shipped a reusable, version-controlled **order-exclusion mechanism** and applied it to TEST + PROD with drift-immune validation. **Status: Done.**

## The order
- `8894973` = SellerCloud order ID (`PROD_DG1_GEP.SELLERCLOUD_SQL.CURRENT_MAIN_ORDER.ID`) → warehouse `ORDER_ID = 'SC_8894973'`. Resolved to **exactly one** order via discriminating query (not Amazon — Amazon IDs are `3-7-7` formatted). See [[confirm-consumer-source]] discipline.
- **Anomalous**: $0 gross, **−$14,755.02 net**, $5,360.92 COGS, **−$20,115.94 margin**, 6 Denis Wick lines, order date 2026-06-09 — a refund/adjustment with no offsetting sale. Excluding it corrects the numbers **upward** (net +$14.8K, margin +$20.1K).

## Mechanism — dedicated exclusion view
- New `WAREHOUSE_SOURCE.SALES_DIM_ORDER_EXCLUSIONS` (`clients/GEP/snowflake/warehouse/sales_dim_order_exclusions.sql`): a static, version-controlled `SELECT … FROM VALUES` list (ORDER_ID, reason, requester, date).
- Referenced from `sales_dim_order_base.sql` via a **NULL-safe `NOT EXISTS`** (not `NOT IN` — a NULL in a `NOT IN` list silently drops *all* orders).
- **Why it propagates everywhere:** `SALES_FCT_ORDERLINE` INNER JOINs `SALES_DIM_ORDER` (← `SALES_DIM_ORDER_BASE`). Removing an order at the base view drops all its lines from the fact and therefore every downstream `REPORT_COMMON` view + PBI model — sales, COGS, returns, margin, order counts — retroactive and forward. One filter, complete removal.
- Future exclusions = add a VALUES row + redeploy that one small view (load-bearing order-base view untouched). Self-service graduation tracked in [[GP-284]].

## Deployed + validated (evidence)
- TEST (`og35375` / GEP Test Models) and PROD (`wj66376` / GEP Prod Models): exclusion view deployed; order-base view + order/dim/fct tables rebuilt; grants preserved (deploy-as-owner + `COPY GRANTS`/explicit re-grant + ownership restore to `CORE_SVC`, per [[snowflake-deploy-grants]]).
- **Drift-immune shadow diff** (the key validation): stand up a shadow of the *original* no-exclusion view and diff order-ID sets against the deployed view at the same snapshot → change = **exactly SC_8894973, zero other orders**. This was essential because the warehouse build reads a live, moving source ([[accumulating-source-tables]]), so a plain before/after grand-total comparison conflates the change with source drift.
- PBI before = 6 lines / −$14,755.02; after refresh = **blank**, both models.
- Rollback DDL captured per env: `warehouse_ops/_exclude_order_ROLLBACK_{TEST,PROD}.sql`.

## PROD scoping gotcha (important)
Deploying the repo `sales_dim_order_base.sql` wholesale to prod would have changed **1,175 orders beyond the exclusion** — all Amazon **UK** orders, because the repo/`development`/TEST carry a newer UK branch that **prod Snowflake does not run**. The prod deploy was therefore scoped to **prod's own baseline + the exclusion only** (injected the `NOT EXISTS` into prod's captured DDL). See the comment on [[GP-282]] and [[gep-snowflake-pbi-deployment]] § "development is an integration branch".
