# GP-328 — MAP Violators grid shows a blank seller row on every client vendor dashboard

**TEST complete, all gates pass. PROD promotion NOT started.** Found while working [[GP-327]];
not caused by it.

## ⭐ The durable lesson — a dimension narrower than its fact

**When a dimension covers a narrower window than the fact it describes, any timeframe wider than
the dimension produces a blank member — and it renders as missing data, not as a modelling
artefact.**

Here: attribute columns came from `REPORT_COMMON.NAVIRA_MAP_VIOLATORS_OVERVIEW` (**last 90 days**,
746 sellers); measures came from `WAREHOUSE.NAVIRA_MAP_VIOLATORS` (**full history**, 1,602 sellers).
The dashboards default to **Year-to-date** (~238 days) and the MAP component has
`ignore_global_filters: false`. Every fact row for a seller that had since dropped out of the
90-day window had no dim row, so DAX collapsed them all into one blank group.

**274 of 1,019 sellers (26.9%), 11,163 rows, 69,130 violations**, across 21+ client dashboards —
visible right now, because YTD is the default timeframe.

## How it was proven (worth copying)

The warehouse **could not** answer this and actively misled: zero NULL seller IDs, zero orphan keys
against the overview. Three pre-registered hypotheses (null-in-source / unmatched-key / window-skew)
were all refuted at the warehouse layer. A fourth (seller with missing name) looked right and was
also wrong.

The answer only appeared **at the consumer's layer** — DAX against the PROD model — and only once
the *dashboard's* timeframe was used rather than the *visual's*:

| Window | Blank row |
|---|---|
| 90 days (the visual's own timeframe) | **absent** — all 13 rows named |
| Year-to-date (the dashboard default, what the client sees) | **present at exactly 1,347** |

Reproduced figure-for-figure against the client's screenshot — four independent figures matching on
every row (Focus Camera 7,947 · BattlBox 2,966 · BladeHQ 1,459 · blank 1,347 · Red Dawg 1,148).
The blank row turned out to be **five real, named sellers** whose names sit in the daily fact and
are simply unreachable through the dimension.

⚠ **A SQL rebuild scoped on `BRAND LIKE '%CONDOR%'` did NOT reproduce the grid**, because the
dashboard scopes on `Product[Default Vendor]` and reaches MAP through relationships — the [[GP-312]]
vendor↔brand naming divergence. Scope a reproduction the way the *consumer* scopes it, not the way
the data is shaped.

## The fix — additive, and why "additive" was load-bearing

**9 of 24 MAP measures are defined ON the 90-day dim** (`MAP Sellers`, the three `(90d)` totals and
rate, `MAP Sellers (Meets Min ASINs)`, and the three `(Floor)` measures). Widening or replacing that
table would move all nine — `MAP Sellers` by **+115%**. But the **four measures the client's grid
actually shows are all fact-only**, so the grid uses the dim *only* for attribute columns.

Hence: **add** a second all-history seller dimension, change nothing existing.

1. `REPORT_COMMON.NAVIRA_MAP_SELLER_DIM` — one row per seller over all history, each attribute
   taking its most recent **non-null** value independently (so a seller named in March keeps that
   name when August rows are blank). Empty strings normalised to NULL first.
2. Model table `'MAP Seller'` + one relationship `'MAP Violators Daily'[Seller ID] → 'MAP Seller'[Seller ID]`.
3. Repoint the shared client visual `63d41094`'s five field references. **PROD-only, not yet done.**

**TEST results:** all 9 dim-exposed measures unchanged, delta exactly **0.0**; overview `HASH_AGG`
checksum identical; unmatched sellers 0; and the grid reconciles — old blank row 33,782 → 0, with
**150 newly-named rows summing to exactly 33,782**. Nothing invented, nothing lost.

## Gotchas earned

- **A newly added relationship does not hold data until `RefreshType.Calculate`.** Until then every
  query across it fails with *"references a relationship … which does not hold any data because it
  needs to be recalculated"* — a build step, not a data problem.
- **The vendor filter is inert in TEST.** `Product[Default Vendor]` does not reach the MAP tables
  there (every vendor returns the all-vendor total), so the TEST demonstration is model-wide, not
  vendor-scoped. In PROD it does propagate. Adjacent to [[GP-312]].
- **The client visual exists only in PROD**, so the field-repoint step is unrehearsable on TEST.
  TEST's five MAP visuals are the *internal* design and must **not** be repointed — they pair the
  dim's own 90-day columns with 90-day measures and are correct as they stand.

## Separate findings, filed not fixed

- **124 of 745 in-window sellers (16.6%) have no name and no business name**, and have *never* had
  one. The unnamed share of daily rows **doubled since February** (4.6% → 10.9%), a gradual drift
  with no cliff. GP-328 surfaces these by Seller ID rather than merging them away; it does not fix
  them.
- **`Product[Default Vendor]` has its own blank member** carrying 1,048,799 YTD violations — the
  same defect class on a different dimension. Internal dashboards would see it; client dashboards
  lock a vendor.
- The **≥3 catalogue floor from [[GP-261]] is absent from the client surface** — the shared visual's
  `options.filters` is empty and the overview view only emits a `MEETS_MIN_ASINS_LISTED` flag.
