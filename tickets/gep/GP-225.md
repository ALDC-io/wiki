# GP-225 — Unified Marketing Schema Design (Snowflake)

**Type:** Story (Scope/Design) | **Status:** Consulting/Design | **Sprint:** S3 | **Sizing:** 2 SP | **Assignee:** Paul Russell
**Roadmap:** [[phase-1a-marketing-ad-platforms|Phase 1A]] — prerequisite for all non-Amazon marketing connectors.

Design the unified Snowflake marketing schema that every Phase 1A connector (Google Ads, Meta, Amazon UK PPC, Target+) feeds into, to enable cross-channel ROAS. Two-layer target: `MARKETING_RAW` (source-specific staging) + `MARKETING_ANALYTICS` (unified grain), with a `REPORT_COMMON` view layer for BI consumption.

## Key Finding — the unified schema already largely exists

`MARKETING_FCT_ACTIVITY` (`clients/GEP/snowflake/warehouse/marketing_fct_activity.sql`) **already unifies** all channels into a single grain via a 7-branch `UNION ALL`:

- Branches 1–5: Amazon Ads SB (ASIN-level + non-ASIN fallback + legacy), SP, SD
- Branch 6: Google Ads (via [[Windsor]])
- Branch 7: Meta/Facebook (via [[Windsor]])

Common grain: `PLATFORM, CAMPAIGN, AD_GROUP, PROFILE, PRODUCT_ID, ACTIVITY_DATE, MARKETPLACE, ENTITY_CODE` with SHA2 keys. Metrics: `CLICKS, IMPRESSIONS, CONVERSIONS, COST, SALES_AMOUNT, UNITS_SOLD`. A sibling view `MARKETING_FCT_PLATFORM_DETAIL` carries platform-specific columns (Google ROAS / impression-share, Meta reach / video).

So GP-225 is mostly **formalizing** what exists (RAW/ANALYTICS layering + `REPORT_COMMON` views + closing the revenue gap below), not green-field design. The "extend `MARKETING_FCT_ACTIVITY` vs build parallel" decision in the ticket is effectively answered: extend — the unification already happened and [[GP-199]] already conforms to its grain.

## Open Questions (from [[phase-1a-marketing-ad-platforms]])

### Q3 — Attribution window & model → **store raw, do not normalize**

The production schema has effectively already decided this: each branch carries the platform's **native** attribution as-is; there is no cross-channel normalization layer, and the ticket itself warns that normalizing attribution across channels "is a project in itself."

- Amazon SP/SD surface the **30-day** window columns (`PURCHASES30D`, `SALES30D`, `UNITSSOLDCLICKS30D`) — the SP advertised-product template requests only the `*30d` fields. Amazon's *API default* is 14-day, but the report exposes 1d/7d/14d/30d and ALDC chose 30d.
- Google conversions arrive via Windsor per the account's model (data-driven by default).
- Meta would arrive per its window (7-day click / 1-day view) — once revenue is actually pulled (see gap below).
- [[Windsor]] only ever returns platform-native attribution and can't be re-windowed historically, so "store raw" is also the only *practical* option.

**Design decision:** store raw per-platform attribution in `MARKETING_RAW`; for Amazon, persist all available windows and surface 30d as the headline in `MARKETING_ANALYTICS` to match prod. Do **not** build a normalized cross-channel attribution model.

**Amazon headline window — DECIDED 2026-05-29 (Paul): keep 30-day** (matches current prod `*30D` columns; revisit only if Navira requests otherwise). Remaining soft confirm for Lori/Heather: she's OK seeing each platform on its native window, clearly labelled, side by side.

### Q8 — Campaign → SKU mapping → **partially answered by [[GP-199]]; no ASIN→internal-SKU dimension exists yet**

The unified fact already has a `PRODUCT_ID` / `PRODUCT_KEY` grain. [[GP-199]] populates it with **ASIN** for Amazon SB (via `EXTRACT_AMAZON_ADS_SB_AD_ASIN_MAP`); SP uses `ADVERTISEDSKU`. Google/Meta rows set `PRODUCT_ID = '-1'` (no SKU linkage).

**The gap, re-characterised (2026-05-29):** `SALES_FCT_ORDERLINE.PRODUCT_ID` uses internal SKUs (e.g. `FBM_AUTO10W`); ad data uses ASINs (e.g. `B0GT2G514J`). An ASIN↔internal-SKU bridge **does exist** — `SHARED_DIM_PRODUCT_BASE` maps `ASIN`/`PARENT_ASIN` ↔ `PRODUCT.ID` from the Sellercloud product master. So the real gap is **(a)** that bridge isn't wired into the unified ad fact's `PRODUCT_ID` resolution, and **(b)** coverage — advertised ASINs absent from Navira's Sellercloud master won't resolve (the UNK case GP-199 deferred). For *agency* customers the master doesn't cover their ASINs at all, so each needs its own product dim. This bridge is what enables Amazon product-grounded ROAS — see [[cross-channel-marketing-attribution]]. Google (UTM) and Meta (catalog) SKU linkage is a later extension (gated Phase 2).

> **Q8 detail handed off to a separate session.** Full SKU-mapping design not yet finalized here.

## Cross-Channel ROAS Gap — Google/Meta revenue is not loaded (the real blocker)

This is the biggest finding and the actual blocker behind "true ROAS across channels" — bigger than attribution-window alignment. It is **not** a [[Windsor]] capability gap; it's a field-selection + mapping gap.

> **Connector context:** Google/Meta are pulled via **Eclipse** (`windsorai_v1` connector, GEP account `da8904db`) into the legacy connectors repo — **not** Prefect (that migration is shelved, 2026-05-28). All template + warehouse-SQL changes below are Eclipse work; "client code" is **GEP**, not `GEP_PREFECT`.

| Branch | Today | Why |
|---|---|---|
| Google (6) | loads `CONVERSIONS`; hardcodes `SALES_AMOUNT = 0` | Windsor Google template (`templates/windsor/google_ads.json`) doesn't select `conversions_value` (it does carry `roas`). Clone of Fusion92's template, which never pulled revenue. |
| Meta (7) | hardcodes `CONVERSIONS = 0` **and** `SALES_AMOUNT = 0` | Windsor Meta template (`templates/windsor/meta_ads.json`) only selects **video-view actions** — no purchase actions, no `action_values`. Same clone gap. |

=> Cross-channel ROAS cannot be computed until revenue is loaded for Google/Meta. **Creds were verified 2026-05-29**, so the external blocker is gone — what remains is warehouse work.

### Work to close the gap (next increment)

1. **Google template** — add `{"name": "conversions_value"}` (VERIFIED present 2026-05-29; pairs with existing `conversions`). Also available: `all_conversions_value`, `conversion_value`, `adnetwork_revenue`, and `roas` (already pulled but unused). Hold back `all_conversions_value` for now — view-through double-counts + row-split risk.
2. **Meta template** — add purchase conversions + value. **Field names VERIFIED 2026-05-29** against live `GET https://connectors.windsor.ai/facebook/fields?api_key={KEY}`: use **`actions_purchase`** (count) + **`action_values_purchase`** (value). Variants that exist: `actions_omni_purchase`/`action_values_omni_purchase` (note PLURAL "values"), `actions_offsite_conversion_fb_pixel_purchase`/`action_values_offsite_conversion_fb_pixel_purchase`. **Do NOT use `action_value_omni_purchase`, `purchases`, `purchases_value`, `purchase_roas`, `website_purchase_roas` — these do not exist in Windsor's catalog** (the earlier candidate guesses were wrong).
3. **Mock SQL** — add `CONVERSIONS_VALUE` to `mock_google_ads_raw.sql`; add purchase-action + `ACTION_VALUES_PURCHASE` columns to `mock_meta_raw.sql`, or the revenue path isn't exercised in the clone.
4. **`marketing_fct_activity.sql`** — Branch 6 `SALES_AMOUNT = SUM(G.CONVERSIONS_VALUE)`; Branch 7 `CONVERSIONS`/`SALES_AMOUNT` mapped to the new Meta fields.

> ⚠️ **Row-splitting gotcha** (both template comments warn): some Windsor field combinations split rows (same PK, partial data each) and corrupt the Snowflake merge. After adding fields, test one day grouped by PK for >1 row **before** full activation. Meta is the high-risk one.

> ⚠️ **Cross-client account filter**: the Windsor team API key pulls **all** Fusion92 accounts too — a per-client account filter must be built into the GEP Windsor templates before real-TEST/Eclipse activation. See [[project_windsor_fusion92_filter]].

### This delivers per-channel ROAS only — not cross-channel truth

The Windsor revenue fields above are **platform-attributed** conversion value (each platform's own pixel + window). They double-count across channels and won't reconcile to actual orders in `SALES_FCT_*`. So this gap-close gives correct **per-channel** ROAS (Tier 1) — valuable for in-channel optimisation — but is **not** a cross-channel source of truth. The grounded model (blended MER + Amazon product-level, denominator = real orders) is designed separately in **[[cross-channel-marketing-attribution]]** and needs its own ticket. Don't mark "true cross-channel ROAS" done off the back of GP-225.

## Relationship to [[GP-199]] — no rework; safe to promote

GP-199 (SB ASIN spend allocation) is **not impacted** by Q3 or Q8:

- It is a **cost-allocation** feature only — its branch sets `CONVERSIONS=0, SALES_AMOUNT=0, UNITS_SOLD=0` and only allocates `ASIN_ALLOCATED_COST`. Q3 concerns sales/conversion columns it doesn't touch.
- It **conforms to** the unified grain (populates `PRODUCT_ID` with ASIN) and **implements** the Amazon-SB answer to Q8.
- The only thing that would force GP-199 rework — switching SB to purchased-product attribution (Approach B) — was explicitly **rejected by Justin Shuster on 2026-05-01**.

=> GP-199 prod promotion does **not** need to wait on GP-225.
