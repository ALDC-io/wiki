# GP-286 — CSV connector silently drops entire file on non-UTF-8 input

**Bug.** The Eclipse CSV connector aborts the whole file when a supplement CSV contains a single non-UTF-8 (Windows-1252) byte, leaving the downstream warehouse table stale with no alert. Surfaced by Navira (Heather) when the quarterly **Account Managers** CSV stopped updating the data model.

## Status

`resolved` (fix deployed to both prod agents 2026-07-07; awaiting daily warehouse rebuild for full model propagation).

## Symptom

Navira updates the Account Managers CSV in [[nextcloud]] each quarter (brands move between managers). The 2026-07-06/07 upload landed in NextCloud but the data model did not update.

## Root cause

`BaseConnectorFlat.open_csv_file` (repo [[connector]], `connector/base/base_connector_flat.py`) opens supplement files with Python's **default UTF-8 codec**:

```python
with open(location, newline='') as csvfile:
    reader = csv.DictReader(csvfile, ...)
```

The new file contained one non-UTF-8 byte — `é` stored as Windows-1252 `0xe9` in the brand **"Solé Bicycles"** (manager `Unassigned Brand`). `csv.DictReader` raised `UnicodeDecodeError` on that byte and aborted the **entire file before any row was parsed** → no schema, no `SESSION INIT`, no staging table, no merge. The exception was swallowed by the run loop (schedule marked complete), so **no alert fired** — the same silent-degradation class as [[GP-PENDING-infra-connector-failures|GP-269]].

The connector's own `clean_value()` strips leading tabs and `clean_key()` uppercases the header (so `Brand` → `BRAND`), so those file quirks were red herrings — the decode was the sole failure.

## Evidence (prod, verified)

- Infra healthy: agent container `agent-dcgeneral-coquitlam-master` up, `Privileged=true`, CIFS mount populated; new file present on the mount (Jul 6/7, 112 data rows).
- Every sibling CSV supplement (Marketplace, Forecast, SKU Kits, Company Name, State Names, Sellercloud Channel Map) refreshed normally 2026-07-07 08:49 PDT.
- `PROD_DG1_GEP.SUPPLEMENT.ACCOUNT_MANAGER_CSV` frozen at `last_altered = 2026-06-16`, 271 stale rows; **zero** `SESSION INIT` for category `ACCOUNT_MANAGER`; no ~112-row staging table created Jul 6/7.
- Reproduced on the real file: UTF-8 open → `UnicodeDecodeError: byte 0xe9 in position 2867`; cp1252/latin-1 → parses cleanly to 112 rows.

## Fix

**Immediate (data).** Re-encoded the NextCloud file to UTF-8 in place (content otherwise byte-identical; original backed up). NextCloud sync is bidirectional (`nextcloudcmd`), so the correction also propagates to the server. Connector reloaded on its next cycle — `ACCOUNT_MANAGER_CSV` now **112 current active rows** (`HISTORY_CURRENT=1 AND DELETED=0`), `last_altered` 2026-07-07 09:52 PDT, "Solé Bicycles" present. (Physical row count 276 = 112 live + 164 soft-deleted old brands.)

**Permanent (code).** `connector` PR #126 (branch `fix/paulrussell/gp-286/csv-encoding-tolerance`, merged `c3a1ac4`):
- New `read_csv_rows()` tries encodings **utf-8-sig → cp1252 → latin-1** (latin-1 maps all 256 byte values, so it never raises), logging when a fallback is used. Valid UTF-8 files decode first-try — unchanged behaviour.
- `open_csv_file()` now raises a hard error on a zero-row parse instead of silently returning empty.
- Regression tests: `tests/test_connectors/test_flat_csv_encoding.py` (5 passing), incl. the real cp1252 byte pattern.

## Gotcha (for future connector work)

The legacy Eclipse `BaseConnectorFlat` CSV reader assumes UTF-8. **Client-exported CSVs are frequently Windows-1252** (Excel / Google Sheets on Windows), and a single accented character (`é`, `ñ`, smart quotes, …) will silently drop the whole file with no alert. Any new CSV-reading code must decode with an encoding fallback. See also the sibling silent-failure mode (privileged-mount CIFS drop) in [[connector-docker-deployment]] § Pitfalls.
