# GP-311 — SKU Profitability over-counted Orders

Navira reported **2 units / 8 orders** for W29. The Data Model was correct; the dashboard was wrong.
Resolved by nulling a synthetic business key at the **fact** layer, which corrected every SQL
consumer at once. Second occurrence of the same defect — [[ALDC-490]] fixed it five weeks earlier at
the *consumption* layer, and that could not generalise.

Ran as an [[inquest-bug-resolution]] council of five. The council caught **six factual errors in the
inherited case file before any of it reached a partner.**

## The mechanism

`SALES_FCT_ORDERLINE` carries synthetic placeholder rows parking ad spend that produced no sale
(`sales_fct_cost.sql:216-253`, gated on `ORDER_LINE_COUNT = 0 AND COST > 0`): `LINE_STATUS='Unknown'`,
`ORDER_ID='UNK_<date>_<ccy>'`, 0 units, 0 sales. **Those rows are by design and correct** — without
them no-sale spend vanishes from ACOS/TACOS.

**The defect is that a synthetic row was given a real-looking business key**, so
`COUNT(DISTINCT ORDER_ID)` — the obvious way to count orders — counts advertising events as sales.

Fix, in the view's **outer projection**:
```sql
CASE WHEN LINE_STATUS = 'Unknown' THEN NULL ELSE ORDER_ID END :: VARCHAR AS ORDER_ID
```
`COUNT(DISTINCT …)` ignores NULL. `ORDER_KEY` stays populated (see Trap 5) and **the rows stay** —
they carry the money.

## ⭐ Trap 1 — a consumption-layer guard cannot fix a fact-layer defect

ALDC-490 guarded **one DAX measure**. `LINE_STATUS` is filtered **nowhere** downstream of the fact
builds in the whole `clients/GEP/snowflake` tree, so every SQL consumer kept the bug and always had.
The dashboard that re-reported it doesn't use Power BI at all — it posts **raw SQL** to
`/v1/warehouse/query` — so no measure fix could ever have reached it.

**Fix fact-layer defects at the fact.** Patching consumers one at a time is what let this recur
twice (three times counting [[GP-315]]).

## ⭐ Trap 2 — nulling a value can DELETE rows ($423K lesson)

The first fix attempt nulled `ORDER_ID` in the *Unknown branch* that produces it. That branch feeds
`INNER JOIN WAREHOUSE.SALES_DIM_ORDER ON (DIM_ORDER.ORDER_ID = ORDERLINE.ORDER_ID)`. `NULL = NULL`
never matches, so it **eliminated every placeholder row**:

```
rows      3,423,278 -> 2,952,014   (-471,264)
ad spend  $2,305,679.75 -> $1,882,606.80   (-$423,072.95)
```

Deployed, measured, rolled back from a live-captured DDL, verified restored. **Before changing a
column's VALUES, check whether anything selects ROWS by it.** "Smallest change" means smallest blast
radius, not the most local-looking edit — editing one union branch *looks* tighter than editing the
shared output projection and is far more dangerous.

## ⭐ Trap 3 — an absence assertion can be satisfied by destroying the population

The bad deploy printed **"✅ applied and verified"**. Its check was `unknown_rows_with_id == 0` —
trivially true once the rows are gone.

**And it would have survived mutation-testing** (without the fix it reads 471,264 and goes RED). So
mutation-testing proves an assertion is *sensitive to the fix*; it cannot prove it is *insensitive to
catastrophe*. Pair every absence assertion with an **explicit expected value for the population**:
`total_rows == N`, the subpopulation count, both distinct counts, the money column.

**This recurred at the end of the same session** in a consumption probe whose verdict logic treated a
*failed* instrument as a clean negative — printing "NOT CONSUMED" when the query had errored. Fixing
it changed the answer from "nobody reads this" to "four readers including the PBI service account."
**A failed check is not a passing check.** Add positive controls that prove the instrument works.

## ⭐ Trap 4 — the `UNK_` grain is per (date × currency), NOT per ASIN

`ORDER_ID = 'UNK_<date>_<ccy>'` and `ORDER_KEY = SHA2(ORDER_ID)`, so **one key is shared by every
product advertised that day**; the per-ASIN grain lives in `ORDER_LINE_KEY`.

**Severity therefore scales INVERSELY with grain** — and quoting the aggregate alone hides the bug:

| Grain | Inflation |
|---|--:|
| account-wide | **+0.055%** |
| date × brand | +1.14% |
| **per SKU row** | **+3.5% (90d) / +6.1% lifetime**, 18.9% of rows |
| **worst single row** | **1 real order rendered as 82** |

Never sum per-row `unk` to get a scope total — at 90d all-vendors that is 9,632 vs a true 180 (53×
wrong). The date × currency model predicts ALDC-490's own counts to the unit (780 days × 2 − 1 =
1,559).

## ⭐ Trap 5 — fixing `ORDER_ID` leaves `ORDER_KEY` counters exposed

`ORDER_KEY` was deliberately left populated: the guarded PBI measure and the fact→dim relationship
both join on it. Correct trade-off, but it means **any consumer counting `ORDER_KEY` is still
wrong** — which is [[GP-315]] (`RETAIL_DAILY_SALES_FACT:49`, dormant: no PBI reads in ~a year).

## ⭐ Trap 6 — a deprecated column reads $0.00, and a warning citing it gets dismissed

The inherited case file's safety warning named `NOSALE_ADVERTISING_FEE_CONSOLIDATED`. That column is
**hard-coded to `0`** (`sales_fct_cost.sql:172/:211`, deprecated at `extract_sales_detail.sql:30`) —
$0.00 across all 471,266 placeholder rows. Had it been sent, the reader would have checked, found
zeros, and dismissed the whole warning. The real field is
**`PRODUCT_ADVERTISING_FEE_CONSOLIDATED`** — on the reported screen, **41.7% of ad spend**, moving
ACOS 8.76% → 5.10%.

## ⭐ Trap 7 — TEST and PROD objects of the same name can differ structurally

TEST's view carries a `SELECT _ORIG.*, 'NAVIRA' AS ENTITY_CODE FROM (…)` wrapper (35,510 chars) that
PROD lacks entirely (29,892, zero occurrences) — intentional unpromoted agency work.
`GEP/development` tracks deployed **TEST**, not PROD.

**Grants differ too**, so the deploy role cannot be copied: PROD's view is owned by `CORE_SVC` and
carries the `WJ66376.PROD_DG1_GEP` **data share** (3 grants); TEST's is owned by `ACCOUNTADMIN` with
no share (2). Always `SHOW GRANTS` first, deploy as the **owner** role with `COPY GRANTS`, and assert
set-equality after. Two syntax gotchas: `GET_DDL('VIEW', …)` emits an **unqualified** name, and
`COPY GRANTS` must follow the **column list**, not the view name.

## Outcome

- **PROD + TEST** fixed (view + table), all assertions on explicit expected values.
  PROD distinct `ORDER_ID` 2,855,336 → 2,853,757 (−1,579 exactly); `ORDER_KEY`, gross qty, sales, ad
  fee and margin all unchanged. TEST: 485,134 placeholder rows, same result.
- **Rendered QA passed** — Kuvings W29 7/17/2/1/1/2 matching the Data Model 6/6; Condor
  `MS_CTK3941-6.1HC` **82 → 1**; and `TACoS 113.36%` on a barely-selling row proving ad spend
  survived. QA also incidentally exercised the app's *second* code path (the "include products with
  no sales" LEFT JOIN branch).
- **Shipped:** `clients` PR #494 → `GEP/development` (`a4ac6c9`); evidence + rollback maps for both
  environments in `aldc-launchpad` `feature/gp311-sku-orders-overcount` (`c0ef9bd`, `c7bbc1a`);
  regression test in `navira-marketing-dashboard` (`bc21f25`, mutation-proven).
- **Scope is GEP-only, structurally:** the `'UNK_'` generator exists in exactly one file estate-wide.
  Fusion92 has no `sales_fct_orderline.sql` at all; three other clients have one but no placeholder
  rows. **No eclipse-2.1 or core_api deploy** — the affected surface is an external iframe app.

## The app's source could not be found

40+ local repos, all 35 `ALDC-io` repos, GitHub code search on the app's **own SQL** (zero hits), all
4 Azure subscriptions, not Vercel, **no sourcemaps**. The deployed minified bundle is readable — and
is how the mechanism was proven — but not patchable. That is *why* the fix went to the warehouse.
See [[GP-314]] for the defect that has no warehouse-side lever.
