# GP-204 — CSV-Driven Marketplace Metadata (Net Discount, DTC Fee, Amazon Flag)

Replaced hard-coded CASE statements in order-line facts with metadata-driven flags maintained via a self-service CSV. Business users can now control net-discount behavior, DTC fee rates, and Amazon marketplace scope without code deploys. This also subsumes the work originally scoped under [[GP-197]].

## Status

Completed. All QA checks passed. Deployed to test environment.

## Problem / Request

`sales_fct_orderline.sql` contained hard-coded `MARKETPLACE_NAME IN (...)` checks for two distinct purposes:
1. **Net discount logic**: Six marketplaces (Target, Bridgford WooCommerce, Bigso Shopify, Brinno Shopify, Carry-on Shopify, GEP Brands) had special net-sales calculations that subtracted discounts.
2. **DTC fee**: Four Shopify marketplaces had a hard-coded 3% DTC fee applied to gross sales.

Additionally, `sales_fct_cost.sql` hard-coded `('Amazon US', 'Amazon CA', 'Amazon Mexico')` to scope advertising fee allocation (the [[GP-197]] issue).

Every new marketplace required a code deploy to update these lists.

## Design / Approach

### 1. Store behavior flags in the marketplace CSV

Added three columns to `Marketplace Name.csv` (on Nextcloud):
- **`APPLY_DISCOUNT_TO_NET`** (Yes/No) -- controls whether discounts are subtracted from net sales
- **`DTC_FEE_RATE`** (decimal or percentage) -- the DTC fee rate applied to gross sales
- **`IS_AMAZON_MARKETPLACE`** (Yes/No) -- whether the marketplace should be included in ad fee allocation

These flow through [[Eclipse]] into `SUPPLEMENT.CURRENT_MARKETPLACE_NAME_CSV`.

### 2. Register new columns with Eclipse

Updated `GEP/eclipse/templates/supplement/marketplace_name.json` to include the three new fields in the ingestion schema. This keeps ingestion declarative; no manual [[Snowflake]] DDL needed.

### 3. Surface normalized flags in `shared_dim_marketplace.sql`

Pulled raw CSV columns into the dim view with strong typing:
- `APPLY_DISCOUNT_TO_NET_FLAG BOOLEAN` -- case-insensitive parsing (`LOWER(COALESCE(...)) = 'yes'`)
- `DTC_FEE_RATE_PCT NUMBER` -- flexible parsing via regex (strips `%`, spaces; normalizes values >= 1 by dividing by 100)
- `IS_AMAZON_MARKETPLACE_FLAG BOOLEAN`
- Unknown-marketplace fallback rows inherit safe defaults (FALSE / 0)

### 4. Refactor order-line fact

In `sales_fct_orderline.sql`:
- Replaced net-sales CASE with `IFF(APPLY_DISCOUNT_TO_NET_FLAG, SALES_GROSS - REFUNDS - DISCOUNTS, SALES_GROSS - REFUNDS)`
- Replaced DTC block with `SALES_GROSS_TRANSACTION * DTC_FEE_RATE_PCT` (preserving gross base per decision)
- Kept DTC subtraction inside `MARGIN_NET_CONSOLIDATED`

### 5. Refactor cost fact

In `sales_fct_cost.sql`:
- Replaced `WHERE MARKETPLACE_NAME IN (...)` with `WHERE IS_AMAZON_MARKETPLACE_FLAG = TRUE`

### 6. Testing infrastructure

Created a dedicated test pipeline:
- Test CSV at `Client_Tenants/GLOBAL_ECOM_PARTNERS/CSV Supplement/Marketplace Name/MARKETPLACE_NAME_gp204.csv`
- Cloned [[Eclipse]] connection + template in CosmosDB (named `Supplement Marketplace Name GP204`)
- Test views in `WAREHOUSE_TEST_PAUL` schema pointing at test CSV data

## Key Design Decisions

| Decision | Rationale |
|---|---|
| CSV over repo config | Business users can update without code deploys; aligns with existing GEP metadata patterns |
| Eclipse template update over manual DDL | Keeps ingestion declarative; prevents schema drift on re-ingestion |
| Gross base for DTC fee (not net) | Preserves current financial outputs; `SALES_GROSS_TRANSACTION * rate` matches legacy behavior |
| Parse rate flexibly (regex) | Accepts "3", "3%", "0.03" -- reduces CSV entry errors |
| Defer IS_AMAZON in initial PR | Amazon flag scoped as follow-up to reduce review surface; included in final implementation |

## Lessons Learned

1. **Self-service CSV is the right pattern for marketplace-specific business rules.** Eliminates the deploy-per-marketplace bottleneck and puts control where it belongs (with business users who know which marketplaces get which treatment).
2. **Test with a cloned Eclipse pipeline.** Creating a separate connection/template for the test CSV prevented any impact on the production ingestion pipeline.
3. **Flexible parsing in the dim is worth the complexity.** The regex + normalization logic for `DTC_FEE_RATE` handles multiple input formats, reducing friction when analysts update the CSV.
4. **CosmosDB work is manual and time-consuming.** Cloning connections/templates requires portal navigation through `prodcsdbcsdb1c01 > Data Explorer`. Budget ~45 minutes for connection + template cloning.
