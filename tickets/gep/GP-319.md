# GP-319 — designing the Navira Marketing Model, and making it legible

Marketing Model `2d8587b5` in `GEP Test Models` — **the client's live surface**. GP-319 owns three
deliverables: a **design decision** with candidates scored, **client sign-off on correctness** at the
grain their team uses, and an **enablement pack**. It also owns a **gate**: no further
`navira-marketing-dashboard` work (≈80–85% complete) proceeds until the design settles and the
numbers are signed off, and [[GP-318]]'s successor GP-320 does not start until then.

Blocked by [[GP-296]] (the $2.72M divergence, **unassigned** — the last blocker on correctness
sign-off) and GP-321 (staleness, **resolved**).

## The field list IS the user interface

Nicholas consumes this model in Excel PivotTables, so what an analyst can drag is the whole product.
Measured 2026-08-25 against the live model:

```
Marketing 2d8587b5   400 field-list items · 198 visible measures of 383 · 29 visible tables of 42
Daily     66151728   235 field-list items · 111 visible measures of 357 · 20 visible tables of 39
```

⚠ **400, not the 410 that circulated in five boot prompts.** Also 128 of 198 visible measures carry
**no description**, and 30 sit in **no display folder**. That ratio is the problem the enablement
pack has to solve, not decorate.

## ⭐ The finding that explains "they don't like the design"

The model offers **two measures per concept and signals nothing** about which is safe:

| concept | safe at SKU | not safe at SKU |
|---|---|---|
| spend | `Actual - Marketing - Cost` | `Spend (USD)` |
| clicks / impressions / CTR / CPC | `Actual - Marketing - *` | `Ad Clicks`, `Ad Impressions`, `CTR %`, `CPC (local)` |

⚠ **Corrected 2026-08-25, and every prior handoff had it wrong:** this is *not* a cross-table trap.
Four of the five pairs live in the **same table** — `Marketing Measures` — and the unsafe half is
**unguarded**. Only `Spend (USD)` sits on `Marketing Efficiency`. So the trap is inside one folder.

⛔ **And the sharpest fact about the model, which nothing had stated:**
`Actual - Marketing - Cost` — the measure that splits correctly by product and campaign — covers
**Amazon Sponsored Products and Sponsored Brands only**. It is blank for Google, Meta and Sponsored
Display. `Marketing Efficiency[Spend (USD)]` is complete across all five platforms but refuses a
product axis. **So there is no single measure that is both complete and per-product.** That is the
strongest argument for the conformed-core design and it was never put that way.

## Five INERT axes are live here — the crux defect, still open

An **inert** axis neither errors nor blanks: it returns the portfolio grand total on every member, so
it looks perfectly healthy. Measured behaviourally, one DAX query per cell, both controls passing:

| fact | sliced by | members | every row returns |
|---|---|---|---|
| `Sales Measures` | `Campaign` | 400 | 129,902,886.59 |
| `Sales Measures` | `Platform` | 5 | 129,902,886.59 |
| `Sales Measures` | `Marketing Efficiency Product[ASIN]` | 400 | 129,902,886.59 |
| `Marketing Measures` | `Vendor` | 154 | 2,668,277.36 |
| `Marketing Measures` | `Marketing Efficiency Product[ASIN]` | 400 | 2,668,277.36 |

The Daily model **blanks** the same three `Sales Measures` axes. Its guards work; this model's do not.
See [[answerability-guard]].

⭐ **A single-member axis correctly equals the grand total.** The first probe run reported **nine**
inert combinations; four were single-member axes (`Marketplace[Channel Name]`, and
`Agency[Entity Code]` on three facts). Inertness requires a *real split* to have been ignored.
**Without that rule this would have published nine defects where five exist** — the same
false-positive class as calling a blank a zero, in the opposite direction.

## Agency / Lectric — the removal that must happen in one specific order

Paul, 2026-08-25: *no agency data in either model*, and Lectric is being removed. Enumerated:

| | Daily `66151728` | Marketing `2d8587b5` |
|---|---|---|
| `Agency` table | **absent** | present, visible |
| relationships from Agency | 0 | **9** |
| visible entity columns | 0 | **9** |
| measures referencing agency | 0 | **13** (`(All Agencies)`, `(Company Total)`) |

⛔ **`Agency[Entity Code]` is currently the ONLY thing scoping this model to Navira:**

```
Actual - Sales - Gross    all 129,902,886.59   navira 127,139,621.59   LECTRIC 2,763,265.00
Actual - Sales - Net      same 2,763,265.00 remainder
Actual - Cost - COGS      remainder 0.00
Spend (USD)               remainder 0.00
```

⭐ **Lectric carries $2.76M of sales but zero cost and zero ad spend.** So the strip lowers sales,
leaves cost alone, and therefore **raises margin % and raises TACoS/MER** — correct, but it moves
client-visible ratios and must be announced, not discovered. Gross −2.13%, net −2.27%.

**The order is the entire safety argument.** Removing the agency layer *before* a Power Query entity
filter exists publishes another client's revenue inside Navira's totals — strictly worse than the
residue being cleaned. Scope is **2 tables of the 8** carrying `ENTITY_CODE`: `Order Line`
(NAVIRA 3,425,206 / LECTRIC 5,032) and `Marketing Efficiency` (9,548 / 747); the other six are
already 100% NAVIRA, and editing them would be change without effect.

The fix **copies the Daily model's proven idiom verbatim** rather than inventing one:

```
Filtered = Table.SelectRows(V, each [ENTITY_CODE] = "NAVIRA")
```

Rehearsed in `pbi_ops/_gp319_lectric_strip_and_agency_removal.py` — dry-run default, verbatim M
captured before any write, **the apply asserts live M is byte-identical to the capture** so a
concurrent session cannot be silently overwritten, and **phase 2 refuses to run until a gate proves
the remainder is 0.00 AND every Navira anchor is unmoved**. Two checks, because a filter that removed
*too much* would also show a zero remainder. The gate was tested and does refuse. **Not applied.**

Removal order, mirroring the Daily model's 2026-08-13 pass: **13 measures → 9 relationships → 9
entity columns → the `Agency` table.** Tabular refuses any other order. Phase 2 defaults to **hide**
rather than delete: hiding removes the layer from every field list while leaving all DAX resolvable,
and reverts in one edit.

⚠ **The workbook gave drag-lists, not schemas** — a pivot recipe rather than a data model. Design A

A. Still unfixed.

## The §1 boundary, finally recorded

The Daily-vs-Marketing split lived only in a 2026-08-10 comment that said it *"is currently written
down nowhere in Jira"* — and still did not, five sessions later, while four additive changes went
into both models. Recorded 2026-08-25 as Jira comment 36056. Engagement metrics (Impressions,
Clicks, CTR, CPC, CPM + four quantity measures + the `Campaign` table) are **hidden on Daily, visible
on Marketing**; ad spend is visible on both. Verified: zero visible Daily measures depend on a hidden
one, so nothing is orphaned.

⚠ **The apparent conflict with GP-320's "universal core" is not one.** The core-10 is what the
*Marketing* model must report, not what *Daily* must expose. Same metric, core to one model, out of
scope for the other.

⛔ **Still unconfirmed:** the hide rests on a recollection of Heather's ask. The implementing script's
own docstring says *"confirm against the Avoma transcript before this reaches Heather."* Not done.

## Coverage ceilings worth not re-deriving

- Product-keyable ad spend tops out at **84.35%**. `PRODUCT_ID = '-1'` holds **$457,425 (15.6%)** —
  the platform reported a campaign-level aggregate *instead of* a product, so **no join or connector
  fix recovers it.** Render an explicit `(no product key)` row so totals reconcile; **do not
  allocate it** — that is invention.
- **Sponsored Brands resolves at 0%** at product grain: its `PRODUCT_ID` is an ASIN joined as a SKU —
  384/384 ASIN-shaped, 352 match `.ASIN`, **0** match `.PRODUCT_ID`. Worth ~1.05pp.
- `Product[ASIN]` is **not unique** — 9,754 ASINs on >1 row, 89.7% of the table — so a product
  relationship on the product-grain marketing table is **illegal**, not merely undone.
- Amazon Attribution is **live**, $106,513.30 Google→Amazon attributed sales, but **0 of 22**
  campaign ids match a Google campaign name, so per-campaign ROAS is not defensible. Publisher is.

## Cross-model divergence, unresolved

One of them is wrong and neither has been established as right.
