# GP-257 — Navira Amazon UK Sponsored-Products Ad Spend

Bring Navira's **Amazon UK** Sponsored-Products ad spend into the warehouse. UK ad data never flowed because the legacy [[amazon-ads]] connector was **NA-only**; Amazon partitions ad profiles by region endpoint, so UK/EU profiles are only reachable via the EU host. This ticket added EU-region support to the connector and proved the data lands through the real [[Eclipse]] pipeline.

## Root cause

The `amazon_ads` connector hard-coded the NA hosts (`advertising-api.amazon.com` / `api.amazon.com`). UK profile `1236242149887729` (GBP, Global Ecom UK) is only reachable via the **EU stack** (`advertising-api-eu.amazon.com`, LWA token exchange at `api.amazon.co.uk`). A UK/EU-enabled refresh token has existed since 2026-05-08 (vault: `GEP Amazon Ads Refresh Token (UK - 2026-05-08)`) and is a **superset** — it covers 12 EU marketplaces **plus** US/CA/BR/MX, so one connection serves both NA and UK templates.

## Connector fix — PR #125 (`d00fc39`, merged to `development`)

Added to [[amazon-ads]] (`connector/amazon_ads.py`):
- optional **`region`** option (`NA` default = no-op; `EU` re-points LWA + Ads API hosts to the EU stack)
- optional **`profile_ids`** filter to scope a pull to specific profiles

EU-only, **decoupled from GP-199**. Connector prod branch is **`master`** (not `main`). Current `:development` image = `40430ed` (includes `d00fc39`). EU support confirmed baked into the running image.

### Root cause of the prior partial run (241 rows / 33 days) — CORRECTED

> **The earlier diagnosis (visibility timeout / double-dequeue / zombie clog) was wrong.** Proven via Cosmos `schedule` container + git history:

**What was wrong with the original diagnosis:**

- Visibility timeout was **not short**. `core_api/v1/route_work.py` `work_pick` (~line 706) and `work_pick_agent` (~line 966) already hard-coded `60*60*4` = **4 hours** (introduced in commit `5fb7de4`, present in the deployed pick-fix commit `85557db`). The proposed "set visibility = zombie_timeout_override 7200s" would have been a downgrade from 4 hours.
- Re-pick multiplier was **1.00** — each of the 45 partitions in the partial run was scheduled exactly once. No double-dequeue occurred.
- The fix is [[core_api]]-side, NOT connector-side. The connector never touches the Azure queue — it only relays `queue_pop_receipt`/`queue_id` between `/work/pick` and `/work/complete`. The visibility timeout is set in core_api's `/work/pick` (`receive_message`).
- Max real report latency across 959 completed stage schedules = 1,492s (~25 min); p99 ~17 min; 0 reports exceeded 30 min. So a 4h visibility could never be exceeded → double-pickup was impossible.

**Real root cause = OOM.** The backfill executor container (`gp257-uk-validate`) ran `max_threads=4` with no memory limit on a host with only 3.8 GB RAM. Each worker thread's baseline (~900 MB: pandas + snowflake-connector + ODBC) × 4 ≈ 3.6 GB → exit 137 (OOMKilled confirmed). When the executor OOM'd, its in-flight `init` schedules were orphaned. The UK template had no `zombie_timeout_override`, so the sweep used the short default, producing "no eligible work" stalls that a babysitter had to clear 118× in the prior run.

### Fix deployed 2026-06-11

**[[core_api]] — visibility timeout reduced (route_work.py):**
Changed `60*60*4` → `60*60` (1 hour) in **both** `work_pick` and `work_pick_agent`. Rationale: 1h comfortably exceeds the ~25-min worst real report (no double-pick risk — de-risked against 959 stage completions) but lets a crashed executor's message recover in 1h instead of being locked out for 4h. Published via `func ... publish` to the TEST core_api **STAGE slot** (`aldctestfnapcore1c01-stage`), built from a branch off commit `85557db` that deliberately **excludes** [[GP-277]] Fix 2 (`ee5b553`/`b1cc08c`). App verified healthy post-deploy (HTTP 200, GP-199 NA path intact).

**Cosmos — `zombie_timeout_override` set on the UK template:**
Set `zombie_timeout_override = 3600` on template `c55d33b9f80b496497f7b655ae95ea6d`. The template previously had no override; `schedule_init` propagates `template.zombie_timeout_override → schedule`. Coupled with the 1h visibility so a crashed pick's schedule is swept ~when its message reappears.

**Executor — reduced to `max_threads=2`:**
~1.8 GB on the 3.8 GB host. Re-run completed with RestartCount=0, OOMKilled=false (no OOM), no clog, no babysitter clears.

**Rollback recorded:**
- `git checkout 85557db -- v1/route_work.py && func publish --slot stage` restores the 4h visibility
- `_gp257_set_template_override.py --revert` restores the template
