# GP-197 — Future-Proof Amazon Marketplace Filter in Sales Cost Fact

Replace the hard-coded Amazon marketplace name list in `sales_fct_cost.sql` with a metadata-driven `IS_AMAZON_MARKETPLACE` flag so that newly onboarded Amazon marketplaces (UK, EU, JP, etc.) automatically participate in advertising fee allocation without code changes.

## Status

`SALES_FCT_COST` fix shipped via [[GP-204]]. **Remaining open**: `SALES_FCT_COST_ESTIMATES` ship-country filter — in `implementing`, sandbox deploy complete (2026-04-27), sandbox validate pending (session closed before completion).

## Problem / Request

The `ORDERLINE_BASE` CTE in `sales_fct_cost.sql` hard-coded `MARKETPLACE_NAME IN ('Amazon US', 'Amazon CA', 'Amazon Mexico')` to filter order lines eligible for ad fee allocation. When [[GEP]] added Amazon UK, orders from that marketplace were silently excluded from the advertising fee split. Any future Amazon marketplace addition would face the same gap.

## Design / Approach

### Centralize the Amazon definition

1. Add an `IS_AMAZON_MARKETPLACE` boolean flag to `WAREHOUSE_SOURCE.SHARED_DIM_MARKETPLACE` (or a companion view).
2. Logic: `LOWER(COALESCE(MARKETPLACE_NAME, COMPANY_NAME, CHANNEL_NAME, '')) LIKE 'amazon%'` plus explicit aliases for edge cases (e.g., "Amazon.co.uk").
3. Recreate both `WAREHOUSE_SOURCE` and `WAREHOUSE` versions of the dim.

### Filter via the flag

Replace the `WHERE MARKETPLACE_NAME IN (...)` clause in `sales_fct_cost.sql` with `WHERE COALESCE(IS_AMAZON_MARKETPLACE, FALSE)`. Keeps downstream logic untouched and makes the scope auditable.

### Testing plan

1. **Coverage check**: `SELECT DISTINCT MARKETPLACE_NAME FROM WAREHOUSE.SHARED_DIM_MARKETPLACE WHERE IS_AMAZON_MARKETPLACE` should capture all Amazon locales.
2. **Filter diff**: Compare order-line counts before vs after. "After" should be >= "before" (newly included marketplaces only).
3. **Attribution smoke test**: Confirm non-Amazon marketplaces still have zero advertising fee allocation.
4. **Spot check**: Verify specific Amazon UK ASINs now receive non-zero advertising allocations.

## Implementation

The standalone implementation was superseded by [[GP-204]], which added `IS_AMAZON_MARKETPLACE` as one of three CSV-driven columns in the marketplace dimension. The flag is now maintained in the Marketplace Name CSV on Nextcloud and flows through [[Eclipse]] into `SUPPLEMENT.CURRENT_MARKETPLACE_NAME_CSV`, then surfaced through `shared_dim_marketplace.sql` into all downstream facts.

## Lessons Learned

1. **Hard-coded marketplace lists are a recurring anti-pattern.** This was the second instance (after [[GP-169]]'s currency-based inference) of marketplace-specific logic breaking when a new market was added. Metadata-driven flags are the sustainable fix.
2. **Scoping overlap**: GP-197's fix was small enough to bundle into the larger GP-204 refactor, avoiding two separate deploys to the same files.

## Remaining Work — SALES_FCT_COST_ESTIMATES (scoped 2026-04-18)

The `PRODUCT_DATE_COUNTRY` spine CTE in `sales_fct_cost_estimates.sql` still hardcodes
`ADDRESS_SHIP_COUNTRY IN ('CA', 'US', 'MX')`, excluding GB orders from ever receiving
rolling-average cost estimates.

**Fix**: replace the hardcoded list with a dynamic subquery sourced from
`WAREHOUSE.SALES_FCT_AMAZON_ORDERLINE` (Amazon-only by construction, already referenced in
the same SQL):
```sql
SELECT ADDRESS_SHIP_COUNTRY
FROM WAREHOUSE.SALES_FCT_AMAZON_ORDERLINE
WHERE ADDRESS_SHIP_COUNTRY IS NOT NULL
GROUP BY ADDRESS_SHIP_COUNTRY
HAVING COUNT(*) > 10
```
Resolves to `{US, CA, MX, GB}` today; picks up future Amazon markets automatically.

UK country code confirmed as `'GB'` (25 orders on TEST_DG1_GEP). Ireland `'IE'` initially accepted as low-impact (1 order), then excluded via UAT change request — see Change Requests below.

**Why not `IS_AMAZON_MARKETPLACE`?** The flag is in `SHARED_DIM_MARKETPLACE` but not exposed in `SALES_DIM_ORDER` and requires a complex product × location × company join. `SALES_FCT_AMAZON_ORDERLINE` is the cleaner source — it is Amazon-only by definition and already joins in the same view.

**Fallback (Option A)**: If the Amazon-only source causes issues in sandbox, fall back to `WAREHOUSE.SALES_DIM_ORDER` with the same `COUNT(*) > 10` threshold (all order types).

Artifact: `GEP/tickets/GP-197/artifact.yaml`

## Change Requests

### CR-1 — 2026-04-20: Exclude Ireland (IE) from cost estimates

**Client request**: IE orders appeared in the PBI Test Model during UAT. The single IE row caused confusion and the client wants it excluded from the ship-country filter.

**Decision**: Add a minimum order count threshold (`COUNT(orderlines) > 10`) to the dynamic country subquery rather than an explicit `NOT IN ('IE')` exclusion. IE has 1 order and drops out automatically. This approach is future-proof — any thin-data country is excluded without a code change.

**Alternatives rejected**:
- Explicit `AND ADDRESS_SHIP_COUNTRY NOT IN ('IE')` — reintroduces manual maintenance
- Revert to hardcoded allowlist `('CA','US','MX','GB')` — undoes the intent of GP-197

**Status**: SQL updated (2026-04-27), sandbox deployed, sandbox validate pending.
