# GP-304 — Eclipse filter-value endpoint ignores the dashboard's locked filter

A locked dashboard filter is only as strong as the **narrowest route that queries the dataset**.
[[GP-299]] closed the *data* path; the **dimension-enumeration** path was missed and stayed unscoped.
Found during the [[GP-293]] adversarial QA pass, 2026-07-27. **Blocks the GP-293 18-client MAP fan-out.**

**Status (2026-07-27):** fix implemented + unit-tested on branch
`feature/GP-293-fieldvalues-locked-filter` (off `eclipse-2.1`, commit `e6b97a9`). **Not deployed.**
Raised as High, unassigned. Full detail on [[core_api]] § "GP-304 — locked filters did NOT cover the
filter-VALUE endpoint".

## The hole

```
GET /v2/dashboards/{dashboard_id}/dataset/fields/{field_locator}/values/
```

- Authorised by **`Dashboard_View` alone** (`api/dashboards/router.py:119-128`) — the exact grant every
  released client holds on their own dashboard.
- Passed **no locked filters**: `get_dataset_field_values` (`api/datasets/deps.py:54`) had no such
  parameter, and `request_field_values` (`api/datasets/lib.py:182`) issued its DISTINCT query with
  `filters=[], field_filters=[]`.
- **No request tampering needed** — this endpoint populates the filter dropdowns, so it is reachable
  from an ordinary browser session.

The tell that makes it unambiguous rather than a judgment call: the comment on the data route 30 lines
below states *"locked filters are a security boundary and always apply"*. This route applied none — an
oversight against the codebase's own stated invariant. **No GP-299 test touched it.**

## Measured exposure (prod, admin token, read-only)

Against Brinno's dedicated MAP dashboard `af6fdfe7`, locked to `Brand = Brinno` and externally released
to 5 `@brinno.com` users on 2026-07-24:

| Column | Values returned | Lock allows |
|---|---|---|
| `'Brand'[Brand]` | **177** | `Brinno` |
| `'MAP Violators Daily'[Brand]` | 112 | `Brinno` |
| `'MAP Violators by Brand'[Brand]` | 81 | `Brinno` |
| `'Vendor'[Vendor Email]` | **86 email addresses** | — |
| `'Vendor'[Vendor Name]` / `'Product'[Manufacturer Name]` | 153 / 161 | — |
| `'Product'[Account Manager]` | 7 internal staff names | — |

54 of 112 columns enumerable. Rain Bird's dashboard returned the identical 177, so the lock was ignored
**uniformly** — not one dashboard misconfigured.

**Seller identity did NOT leak — but only incidentally.** Every seller column exceeds the endpoint's
**200-cardinality cap** (`Seller ID` 759/1,556; `Other Seller Name` 660) and returns null. The **cap**,
not the lock, was the protection — which would fail silently the day a seller dimension dropped below
200 distinct values.

**What was exposed:** the cross-client dimension catalogue of the shared model — effectively the Navira
brand roster plus vendor contact emails. **Not** seller-level MAP rows, **not** sales figures. That
severity split is why the agreed call was *hold the fan-out, keep Brinno live*.

## Fix

Thread the dashboard's locked conditions through to the query, reusing GP-299's
`dashboards.lib.locked_filter_conditions` so the inclusive-operator whitelist and fail-closed behaviour
are inherited rather than reimplemented. The conditions land in `DatasetRequest.filters` — the *same
slot* the data path uses via `visuals.lib.create_dataset_request`.

**Zero-regression by construction:** a dashboard with no locked filter yields `filters=[]`,
byte-identical to previous behaviour, so the internal all-brands tier is untouched.

`api/visuals/test/test_gp293_field_values_isolation.py` — 11 tests: locked conditions reach the query;
unlocked sends none; `mode:hidden` enforced; a `mode:normal` (user-controllable) filter must **not**
restrict the list; misconfigured operator fails closed; cardinality cap still short-circuits without
querying; RBAC introspection on all three field-values routes.
Suite: pristine `eclipse-2.1` **13 failed/209 passed** → **13 failed/220 passed**. The 13 are
pre-existing `test_pct_change.py` ordering pollution (pass in isolation), verified by stashing the edits.

## Routes confirmed CLOSED (no action)

- `POST /v2/visuals/{id}/data/` → **403** for a client. The RBAC hierarchy is **flat**:
  `build_permission_map` parents every non-account resource to the **account**, so there is no
  dashboard→visual inheritance edge; `external-user` carries `[Account_Access]` only. **This settles
  GP-299's open "Bypass B" question from code — no client tenant was required.**
- `/v2/datasets/{id}/fields/.../values/` and `/v2/data_views/{id}/dataset/fields/.../values/` check
  `Dataset_View`/`DataView_View` via `check_dependency(require_active_account, …)` — against the
  **active account**, which `external-user` lacks. Note the different check shape: account-level
  `Creator` **does** hold both, so any internal Creator can enumerate any dataView's values account-wide.
- Foreign `visual_id` under one's own dashboard → **404** (`api/dashboards/deps.py:22-25`).

## Acceptance criteria

1. As a client-shaped identity (account `external-user` + `viewer` on one dashboard), the endpoint
   returns **only** the locked brand, and no vendor-email/manufacturer values beyond the enforced scope.
2. Internal all-brands dashboards unchanged — full value lists still returned.
3. Filter dropdowns still populate in the Eclipse UI on a locked client dashboard (**rendered** check,
   not just API).
4. `mode:hidden` treated identically to `mode:locked`.
5. Before/after transcripts against the same dashboard.

Deploy: `core_api@eclipse-2.1` → stage slot → swap. One fix covers all 19 dashboards.

## Lessons

1. **Enumerate every route that queries the dataset, not just the obvious data route.** Scoping work
   should start from a route inventory, not from the endpoint the UI happens to call for rows.
2. **A code read can settle what was parked on infrastructure.** GP-299 deferred Bypass B to "the first
   client tenant" for ~4 days; the router dependency plus the role definition answered it in minutes.
   Check whether a question is *actually* environment-blocked before parking it.
3. **A guardrail that protects by accident is not a control.** The 200-cardinality cap was the only
   thing keeping seller identity out — nobody chose that, and nothing would have flagged its erosion.
4. **`email-validator` is missing from core_api's `requirements.txt`**, so `EmailStr` in
   `api/password_reset/schema.py` makes **every** unit test fail to *collect* on a clean install — GP-299's
   included. Those tests run in no environment built from `requirements.txt` alone. Worth its own ticket.

## Update 2026-07-29 — the fix was widened; merge is dead-locked on review

**Status: BUILT, CI-green, NOT deployed. Blocked on a human approving review, not on code.**

### The first fix closed exactly one column

Threading `locked_filter_conditions` into the field-values query (`e6b97a9`, 2026-07-27) is necessary
but **not sufficient**. The query is `CALCULATETABLE(SUMMARIZECOLUMNS(<col>), KEEPFILTERS(<lock>))`,
and **that shape narrows only columns on the same table as the locked column.** Measured on prod
against Brinno's `Brand='Brinno'`-locked `af6fdfe7`, with the fix applied:

| Column | result |
|---|---|
| `'Brand'[Brand]` | 177 → **1** ✅ |
| `'Product'[Brand]` | 177 → **177** ❌ |
| `'MAP Violators Daily'[Brand]` | 112 → **112** ❌ |
| `'MAP Violators by Brand'[Brand]` | 81 → **81** ❌ |
| `'Vendor'[Vendor Email]` | 86 → **86** ❌ |

Confirmed on the **client-facing dashboard route**, not only in simulation. **Positive control:**
same-table *does* narrow (`Product[Brand]` lock → `Product[Manufacturer Name]` 162 → 1), so filters
apply — they just don't propagate. Adding a measure scopes the brand columns to 1 but leaves Vendor at
86: **`'Vendor'` has no relationship path to `'Brand'`**, so no filter shape can ever scope it.

### The widened fix (`06aa015`)

New `assert_field_is_dashboard_filter()` — the route may only enumerate columns the dashboard
**configures as a filter**, else 404. Prod exposes **54 enumerable columns** while every MAP dashboard
configures exactly **3**, so the rest have no UI function there. **The allow-list is the filter bar**,
so it closes all of them — including the unscopable ones — at zero functional cost. +13 tests (34 in
the two files); suite **13F/243P** (the 13 are pre-existing `test_pct_change.py` pollution).

### ⭐ The lesson: the gate would have lied

`D1` tested the one locator the original probe measured, so it would have gone **GREEN on deploy**
while the roster stayed enumerable via `'Product'[Brand]`. Now sweeps 4 brand-bearing columns × 19
dashboards, plus a new `D5` (sensitive non-brand dimensions must be scoped **or refused**). Both red
pre-fix; D2/D3 green. Also `D4` **skips as `not-openable`** — a locked Brand filter exposes no dropdown
in the UI, which invalidates §1–§2 of the manual QA guide (needs rewriting before use).
