## KPI Definitions

### KPI 1: Return % Per SKU

```
Return Rate % = SALES_RETURNS_QUANTITY ÷ SALES_GROSS_QUANTITY × 100
```

- Data source: both fields already in the product table
- Shown in red when > 0 (consistent with existing Return Units styling)
- Example: 12 returns ÷ 200 units sold = 6.0%
- Unit-based — matches Amazon Seller Central's return rate calculation

### KPI 2: Return Rate at Brand Level

```
Brand Return Rate % = SUM(Brand Return Units) ÷ SUM(Brand Units Sold) × 100
```

- Groups all SKUs under the same brand, applies formula to aggregated totals
- **Correct aggregation: sum units first, then divide** — do NOT average individual SKU percentages
- Example: Brand "AcmePro" has 3 SKUs with 5+8+12=25 returns out of 80+120+200=400 units = 6.25%

## Architecture: How Eclipse Dashboards Connect to Data

The SKU Profitability app in Eclipse embeds a Power BI report — it is **not** a live view to Snowflake.

```
Snowflake → (scheduled refresh) → PBI model → (publish) → PBI Service → (iframe) → Eclipse sidebar
```

**Implications for this ticket:**
- After PBI model is published with the new measures, the Eclipse sidebar app shows them automatically (embeds by report ID — no Eclipse-side change needed)
- The source columns (`SALES_RETURNS_QUANTITY`, `SALES_GROSS_QUANTITY`) are already visible in any Snowflake-connected tool (e.g. Eclipse data explorer) today
- The return rate *percentage* is a DAX measure — it only exists in the PBI model, not in Snowflake. It shows up in any report/dataview connected to that model after publish.
- Lori's vibe-coded dashboards will pick up the new measures once PBI is published + refreshed — no manual wiring on the Eclipse side

## Key Design Decisions

- **Unit-based, not value-based** — Heather confirmed. Unit-based aligns with Amazon account health metrics. Value-based (refund $ ÷ gross sales $) gives a financial view but wasn't requested.
- **Measures, not calculated columns** — Lori's approach. Measures use dashboard time-period context automatically, so no need to bake time-period logic into the formula.
- **Aggregate-then-divide for brand level** — Sum the units across brand SKUs first, then divide. Averaging individual SKU return rates would give incorrect results (Simpson's paradox).
