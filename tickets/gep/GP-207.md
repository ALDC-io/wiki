# GP-207 — Prod-to-Test Data Share Setup

Re-pointed all [[GEP]] warehouse SQL files to use the `PROD_DG1_GEP` data share for raw source tables, so that both test and production environments reference the same underlying data through [[Snowflake]]'s data sharing. This eliminates the divergence between test and prod source data and means test validation runs against real production volumes.

## Status

Completed. All SQL files updated. Five intentional exceptions documented.

## Problem / Request

GEP's test environment (`TEST_DG1_GEP`) previously had its own copies of raw source tables (Amazon, Amazon Ads, SellerCloud, Supplement). These diverged from production over time, making test validation unreliable -- passing tests in TEST did not guarantee correct behavior against production data volumes or data quality. The `PROD_DG1_GEP` data share was already mounted and accessible, exposing the same `CURRENT_*` and `COMBINED_*` views that the repo references.

## Design / Approach

### Two-track implementation

1. **Snowflake UI (non-WAREHOUSE views)**: Re-point raw views directly in the Snowflake UI using `CREATE OR REPLACE VIEW ... AS SELECT ... FROM PROD_DG1_GEP.<schema>.<table>`.
2. **GitHub repo (WAREHOUSE* SQL files)**: Add `PROD_DG1_GEP.` prefix to all raw table references in `GEP/snowflake/warehouse*/` files.

### Scope: 4 schemas, ~50 tables

| Schema | Example Tables |
|---|---|
| AMAZON | `CURRENT_REPORT_ALL_ORDERS`, `CURRENT_REPORT_RETURN`, `CURRENT_REPORT_FBA_INVENTORY`, `CURRENT_REPORT_SALES_AND_TRAFFIC_CHILD`, ~6 more |
| AMAZON_ADS | `CURRENT_SPONSORED_PRODUCTS_*`, `CURRENT_SPONSORED_BRANDS_*`, `CURRENT_SPONSORED_DISPLAY_*`, `CURRENT_API_BRAND`, `CURRENT_API_PORTFOLIO` |
| SELLERCLOUD_SQL | `CURRENT_MAIN_ORDER`, `CURRENT_MAIN_ORDERITEM`, `CURRENT_MAIN_PRODUCT`, ~15 more including `COMBINED_*` history tables |
| SUPPLEMENT | `CURRENT_TIME_CALENDAR`, `CURRENT_MARKETPLACE_NAME_CSV`, `CURRENT_FORECAST_CSV`, ~8 more |

### Batch editing strategy

Replacements were made per schema to enable sanity-check diffs (e.g., all SELLERCLOUD_SQL updates in one pass, all SUPPLEMENT in another).

## Implementation

All files under `GEP/snowflake/warehouse*/` now point at `PROD_DG1_GEP.<schema>.<CURRENT_/COMBINED_*>` except for five intentional exceptions:

### Intentional exceptions (not prefixed)

| Object | File | Reason |
|---|---|---|
| `DUER_ANALYTICS.CURRENT_ANALYTICS_DIM_CALENDAR` | `warehouse_comm_src/shared_dim_date.sql` | DUER_ANALYTICS is not part of the `PROD_DG1_GEP` share |
| `SELLERCLOUD.CURRENT_CUSTOMER_MAIN` | `warehouse/shared_dim_customer.sql` | Share only exposes `SELLERCLOUD_SQL`, not `SELLERCLOUD` |
| `SELLERCLOUD.CURRENT_ORDERS_HEADER` | `warehouse/shared_dim_customer.sql` | Same as above |
| `TEST_DG1_ALDC_LIBRARY.SUPPLEMENT.CURRENT_KPI_PERIODICITY` | `warehouse/shared_dim_periodicity.sql` | KPI CSV lives in the ALDC library, not the GEP prod share |
| `TEST_DG1_ALDC_LIBRARY.WAREHOUSE.SHARED_FCT_EXCHANGE_RATE` | `warehouse/shared_fct_exchange_rate.sql` | Exchange rate view published from ALDC library |

### Discovery findings

- Share is mounted and accessible: `PROD_DG1_GEP` visible via `SHOW DATABASES`, exposes AMAZON, AMAZON_ADS, SELLERCLOUD_SQL, SUPPLEMENT schemas.
- All required raw sources exist as shared views with names matching repo references exactly.
- DUER_ANALYTICS and SELLERCLOUD (without `_SQL`) are not in the share -- documented as known gaps requiring either share extension or continued legacy behavior.

## Testing / Validation

Validation was primarily done during downstream ticket deploys ([[GP-200]] was the first deploy after GP-207 landed). Key observations:

- Row counts and data volumes changed significantly because test now sees production data (much larger dataset).
- Amazon order counts appeared to drop (~622K to ~25K `AMZ_*`) but this was correct: the dedup logic reattributed orders to Seller Cloud with the full prod SC dataset. Total volume (AMZ + SC) grew to ~2.55M.
- Two data-share gaps were discovered and fixed during GP-200 deploy: `CURRENT_MAIN_PURCHASEITEM` and `CURRENT_SPONSORED_PRODUCTS_ADVERTISED_PRODUCT_REPORT` were missing from the share.

## Lessons Learned

1. **Data share gaps surface at runtime, not at deploy.** Objects missing from the share only error when views/tasks try to compile. Consider pre-flighting by SELECT-ing from each `PROD_DG1_GEP.*` reference before triggering the task chain.
2. **Volume step-changes require stakeholder communication.** When test starts reading prod data, the volume jump can look like a bug. Always explain the reattribution effect (Amazon vs Seller Cloud dedup) proactively.
3. **Five exceptions are acceptable but should be tracked.** The DUER_ANALYTICS and SELLERCLOUD gaps should be revisited if the share is extended in the future.
4. **Batch edits per schema reduce review risk.** Grouping find/replace by schema makes diffs auditable and prevents cross-schema mistakes.

## Post-Completion Incident (2026-05-27)

40 additional views were found missing from the share during investigation of Justin Shuster's 403 / stale data report. The two critical missing objects were `AMAZON.CURRENT_REPORT_ALL_ORDERS` and `AMAZON.CURRENT_REPORT_ALL_ORDERS_UK` (added for [[GP-200]] Amazon UK work), which broke `WAREHOUSE_SOURCE.SALES_DIM_ORDER_BASE` and silently failed the `TASK_WAREHOUSE_ORDERLINE_0` chain on `TEST_DG1_GEP` for ~6 weeks.

**Fix:** All 40 missing views added to share + automated sync task deployed at `PROD_DG1_GEP.MAINTENANCE.TASK_SYNC_DATA_SHARE` (daily 05:00 PT). See [[Snowflake]] § Automated Data Share Sync.
