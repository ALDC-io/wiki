# GP-169 — Marketing Activity Marketplace Attribution

Established a deterministic mapping between Amazon Ads profile IDs and [[GEP]] marketplaces so that marketing activity facts (spend, clicks, conversions, sales) can be filtered and rolled up by marketplace. Previously, marketing measures had no relationship to marketplace name because the source reports lacked the information needed for the existing channel/company-based join. The solution replaced currency-based inference with a profile-based mapping.

## Status

Completed (development). Awaiting production deploy approval.

## Problem / Request

Marketing Activity fact rows in `WAREHOUSE.MARKETING_FCT_ACTIVITY` had no `MARKETPLACE_ID` or `MARKETPLACE_NAME`. The existing [[star-schema-convention]] used channel + company to derive marketplace, but Amazon Ads reports (Sponsored Brands, Products, Display) do not carry that data. The only available proxy was `CAMPAIGNBUDGETCURRENCYCODE`, but currency-based inference fails when multiple countries share a currency or new markets onboard. [[GEP]] confirmed via Justin that Amazon profile IDs are 1:1 with country/marketplace, providing a deterministic mapping path.

**Jira**: [GP-169 / DE-006 / REQ-624](https://analyticlabsdc.atlassian.net/browse/GP-169)
**Branch**: `feature/paulrussell/GP-169/establish-relationship-between-marketplace-names-and-marketing`

## Design / Approach

### Core idea: Profile ID as the join key

Each Amazon Ads account has a unique `PROFILEID` that maps to exactly one marketplace. Justin provided the canonical list:

| Profile ID | Country | Currency | Marketplace |
|---|---|---|---|
| 2874274850477920 | US | USD | Amazon US |
| 410071870980733 | CA | CAD | Amazon CA |
| 1359269695432602 | MX | MXN | Amazon Mexico |
| 2944710254877284 | BR | BRL | Amazon Brazil |

### Mapping strategy

Introduced `MARKETPLACE_PROFILE_MAP` as an inline `VALUES` CTE inside `marketing_fct_activity.sql`. Each row maps a profile ID to its canonical `MARKETPLACE_ID` (matching `NULL_NULL_-1_{COMPANY_ID}` format from [[Snowflake]]'s `SHARED_DIM_MARKETPLACE`) and a human-readable name. This was chosen over joining to the shared dim directly because:

- Brazil lacks a canonical `NULL_NULL_-1_174` row in the dim (only product/vendor-specific rows exist).
- Inline values guarantee every profile resolves without depending on upstream dim completeness.
- Future plan is to break this out into a standalone dimension/table once more profiles are onboarded.

### Sponsored Display deferral

The Sponsored Display union branch was initially added to `BASE_METRICS` but commented out per senior dev guidance. Only Sponsored Brands and Sponsored Products feed the fact until downstream consumers are ready for Display spend. The code block is preserved for re-enablement.

## Implementation

**File modified**: `GEP/snowflake/warehouse/marketing_fct_activity.sql`

Changes:
1. Added `PROFILEID AS PROFILE_ID` projection to each adapter union branch in `BASE_METRICS` CTE.
2. Added `CAMPAIGNBUDGETCURRENCYCODE AS CURRENCY_CODE` to each adapter for visibility.
3. Replaced the old `MARKETPLACE_MAP` (currency-based) with `MARKETPLACE_PROFILE_MAP` (profile-based `VALUES` CTE).
4. Joined `BASE_METRICS` to `MARKETPLACE_PROFILE_MAP` on `PROFILE_ID`.
5. Emitted `MARKETPLACE_ID`, `MARKETPLACE_KEY` (SHA2 hash), and `MARKETPLACE_NAME` in the final SELECT.
6. Fallback: unmapped profiles emit `MARKETPLACE_ID = 'UNKNOWN_MARKETPLACE'`.
7. Prefixed all final SELECT columns with `BASE.` and added inline comments.

Validated in personal test schema `WAREHOUSE_TEST_PAUL.MARKETING_FCT_ACTIVITY_GP169`.

## Lessons Learned

1. **Currency inference is fragile for marketplace mapping.** Profile ID is deterministic and future-proof; currency can be ambiguous when markets share codes or when multi-currency profiles onboard.
2. **Canonical dimension rows may not exist for all markets.** Brazil had only product/vendor-specific rows in `SHARED_DIM_MARKETPLACE`, not the canonical `NULL_NULL_-1_{COMPANY_ID}` row. Inline values in the CTE were the pragmatic fix, but a data request should be filed for the missing dim entry.
3. **Adding a union branch (Display) requires stakeholder sign-off** even if technically straightforward. Downstream consumers may not be ready for the additional spend surface.
4. **Always snapshot row counts before/after** when changing fact logic. The Display union accounted for the entire row-count delta and would have been confusing without pre/post comparison.

## Key Decisions Log

| Date | Decision | Rationale |
|---|---|---|
| 2026-02-27 | Use profile ID mapping instead of currency | 1:1 deterministic; currency inference fails across multi-country accounts |
| 2026-03-02 | Plan to break profile map into standalone dim | Multiple facts will need the same mapping; inline CTE is interim |
| 2026-03-03 | Leave Brazil as UNKNOWN_MARKETPLACE | No canonical dim row; avoid hard-coded IDs that drift |
| 2026-03-03 | Comment out Sponsored Display union | Senior dev guidance: parity with legacy until Display approved |
| 2026-03-03 | Keep inline VALUES CTE over shared dim join | Guarantees valid pairs; avoids null marketplace when dim lacks entries |
