# GP-310 — MAP Violators "Error loading data"

A visual with **no `rbac_role_assignment` row fails closed with 403 for *every* user, admins
included** — and only one of Eclipse's two visual-fetch routes checks it. Reported by Navira at the
weekly check-in 2026-07-29; resolved 2026-07-30 by deleting the offending object rather than
granting it. **Status: DONE.** Commit `ee48ec5`, branch `feature/gp293-map-embeddable-component`.

The durable value here is not "a row was missing" — it is the four reusable traps below, three of
which cost real time and one of which caused a wrong deploy.

## ⭐ Trap 1 — the permission map's key set is USER-INDEPENDENT

`PermissionChecker.check` (`core_api/api/permission_checker.py:122`) returns False when
`resource_id not in permission_map`. `build_permission_map` builds that map from
`list_role_assignments(account_id=...)` with **no assignee filter** (line 220).

⇒ A resource with **zero** role-assignment rows is a key-set miss for **everyone in the account**.
An admin token confers no bypass — `is_internal` injects only Account-scoped permissions, never
`Visual_View`.

**Why that matters diagnostically:** "the admin also gets 403" looks like it *rules out* an RBAC
cause. It is in fact the signature of this specific one. Any other RBAC branch would have let the
admin through.

## ⭐ Trap 2 — Eclipse has TWO visual-fetch routes with different guards

| Route | Guard | Used by |
|---|---|---|
| `/v2/dashboards/{d}/visuals/{v}/…` | `Dashboard_View` **only** — the visual's own RBAC is never consulted | `/dashboards/{id}` (view page) + the GP-293 e2e suite |
| `/v2/visuals/{v}/` · `/dataView/` · `/data/` | `Visual_View` **on the visual itself** | `/explorer/dashboard/{id}` (edit page) |

The selector is not the page URL — it is whether `<Visual>` receives a `dashboardId` prop
(`eclipse/src/app/api/coreAPI/visuals/lib.ts:460-479`). `ViewDashboard.tsx:29` sets it;
`EditDashboard.tsx:488-507` deliberately does not, and `DashboardContext.tsx` documents that as
intended.

**⇒ A dashboard can be perfectly healthy on `/dashboards/` and completely broken on
`/explorer/dashboard/`.** Validate BOTH. This single fact is why every admin reproduction — and a
green 26/26 e2e suite — declared the surface healthy while a client was staring at an error.

Related: react-query caches on `["visuals", visualId]` with `dashboardId` **not** in the key, so
one browser session that loaded the working route will not reproduce the broken one.

## ⭐ Trap 3 — "Error loading data" does not mean the data call failed

`eclipse/src/components/visuals/VisualWrapper.tsx:83` renders
`Error loading {isConfigError ? "configuration" : "data"}` — and `isConfigError` is **hardcoded
`false`** at line 164. A *config*-fetch failure therefore still reads "Error loading data". Never
infer which fetch failed from the wording.

## ⭐ Trap 4 — the enforced dashboard lock is `locked_value.value`, NOT `restricted_values`

`explorer_dashboard.filters[]` carries both. `restricted_values` is the **dropdown allow-list** and
is frequently `[]` on a hard-locked filter. Reading it reports every dashboard as unlocked. See
[[GP-312]] — this compounds with vendor/Brand name disagreement.

## The false premise that created the bug

[[GP-293]] concluded that a `Product[Default Vendor]`-locked dashboard **cannot** scope a MAP tile
(MAP is keyed on `Brand[Brand]`), so each client needed its own **clone** carrying
`options.filters = Brand[Brand]='X'`. That clone — created by a raw Cosmos insert that wrote the
visual but not its RBAC row — *was* the defect.

**The premise is false.** The model carries a bridge:

```
Product[Default Vendor] → Product[Brand] ══BothDirections══> Brand[Brand]
                                                                 │ OneDirection
                                                    MAP Violators Daily[Brand]
                                                    MAP Violators by Brand[Brand]
```

Measured on the existing shared visual `63d41094`, PROD `74a529b3`:

| Lock | Rows |
|---|---|
| `Product[Default Vendor]='Brinno'` | **11** |
| `Brand[Brand]='Brinno'` | **11** |
| none | 751 |

Exact parity. **Negative control:** the same filter counted via `Navira MAP Violators` (seller
grain) stays at 750, because that edge is many→one and cannot propagate — one table narrows, the
other does not, which is what proves the narrowing is real propagation and not a side-effect.

⇒ **Embed the existing shared visual; build nothing.** No clone, no new RBAC row, no 403, no new
grant surface. See [[map-violators-component-pattern]].

## The wrong fix, and why it was reverted

Writing the missing RBAC row cleared the 403 **and** made
`POST /v2/visuals/{id}/data/` return 743 sellers (all brands) against 6 on the dashboard-scoped
route — the clone's own `options.filters` is **not applied on the direct route**. GP-293's tamper
battery had proven self-scoping on the *dashboard-scoped* route only; that guarantee does not carry.
Applied and reverted; net change to prod zero.

**Recorded honestly:** that measurement used an **admin token**, which cannot distinguish
"internal-allowed" from "client-reachable", and the shared `63d41094` behaves identically. So it was
pre-existing behaviour, not something the fix introduced. Whether it is client-reachable remains
**unproven** and needs the client-scoped identity of [[GP-293]] §7d.

## Method notes worth keeping

- **A safety check that cannot fail proves nothing.** The first scope check "passed" because *no
  data came back at all* — both branches predicted the same observation. Re-run with a valid
  payload, it exposed a real problem.
- **A DAX `VAR` evaluates once, eagerly.** Wrapping it in `CALCULATE` does nothing. This produced a
  confident false negative ("the measures ignore the timeframe") that was stated before re-testing.
- **`AppServiceHTTPLogs` is a first-class forensic source** — it records what each identity actually
  received, so a client-only failure is visible without impersonation. ⚠ Rows contain live session
  tokens in `Cookie` and real client IPs: project neither, pseudonymise IPs. `first`/`last` are
  reserved words in KQL.
- **Trust live data over a prior write-up.** `gp293.md` §3b said the 5 external `@brinno.com` users
  held grants on the dedicated dashboard *only*; the live check disagreed, and the live check won.

## The check that would have caught this

**No prod `explorer_visual` may have zero `rbac_role_assignment` rows.** At the time of the
incident: 64 visuals, 63 covered, exactly 1 orphan — and that orphan was the failure. A single
enumerable invariant, cheap to run in CI. Not yet built — see Open.

## Outcome

MAP Violators is now a **component on each vendor's existing dashboard** (Heather's requirement),
not a standalone per-vendor dashboard. Live for NAVAC, Suitical, Penn-Plax, Coxreels, Condor, G7th,
Dalen, Rain Bird. Removed from Brinno entirely. 19 dedicated MAP dashboards retired (prod dashboards
60 → 41). Internal `eaa10f9e` swapped to the same visual so internal and client match.

The two MAP-only filters (`Selling FBA`, `Min Avg ASINs Listed`) were **restored** to the vendor
dashboards — an audit found 21 of 23 MAP dashboards carried them and the only two without were the
vendor dashboards, so migrating would have silently dropped two client controls.
`Min Avg ASINs Listed` is the [[GP-261]] catalogue-size floor: at ≥3 ASINs/day it drops 83 of the 92
always-100% single-ASIN "violators" while keeping every legitimate business.

## Open

- **CI invariant** (no zero-RBAC visual) — not built.
- **Client-scoped test identity** ([[GP-293]] §7d) — still unprovisioned.
- **Seller roster does not shrink with the timeframe** — only measures respond; zero-violation
  sellers still list. Consequence of the many→one edge above.
- **Date table may not be marked as a date table** — `DATESYTD` returns blank in DAX. Does not
  affect Eclipse's timeframe control (rendered QA passed) but will bite time-intelligence DAX.
- Rendered QA covered NAVAC, Condor and the Brinno removal; the other 6 tiles and internal
  `eaa10f9e` are data-layer verified only.
