# GP-318 — making the Daily Sales Model right before the design phase

The Daily Sales Model (`GEP Test Models` → `Data Model`, dataset `66151728` — the client's **live**
surface, two reports bound) had a marketing layer that was disconnected. GP-318 is the sequence of
fixes making it reviewable before [[GP-319]]'s design phase runs *on* it.

Items 1–3 carry a Snowflake **write approval scoped to those three items only** (Paul, 2026-08-12).
Items 1 and 2 are spent; item 3 remains.

## Item 2 — the durable Meta fix: a scoping premise refuted by measurement

The most transferable thing in this ticket. Item 2 was scoped as *"the durable Meta fix in the
warehouse view"*, naming `MARKETING_FCT_ACTIVITY_UNIFIED`, with the broken
`MARKETING_FCT_ACTIVITY_GOOGLE_META` (B16) expected to be fixed alongside it. **Neither object was
involved.**

Meta rendered a literal `0.00` for 22 of 27 months — NOT-RECORDED presenting as ZERO, the same class
of error as [[GP-317]]'s UK allocation. Tracing the consumer route rather than trusting the premise:

```
[Spend - Meta]  →  model table 'Marketing Efficiency'
                →  REPORT_COMMON.MARKETING_EFFICIENCY_MARGIN
                →  REPORT_COMMON.MARKETING_EFFICIENCY
```

`MARKETING_EFFICIENCY` pivots platforms by `UNION ALL` using **`0` as the "not this platform"
filler** (`0 AS SPEND_USD_META`; `IFF(PLATFORM_ID='Meta Facebook Ads', SPEND_USD, 0)`). Amazon rows
begin 2024-06-01 and Meta's first activity is 2026-04-20, so every month between inherited a literal
zero. The activity fact was innocent throughout — 531 Meta rows, none before 2026-04-20, no date
spine, no coercion. A `SUM` over no rows is already BLANK.

**Fix:** derive Meta's first activity date *inside* the view and emit `NULL` before it; keep `0`
after, so genuine post-launch zero days survive. Applied to `PLATFORM_ATTR_SALES_USD_META` too — the
identical defect on a sibling metric.

⭐ **The lesson generalises past Meta:** a UNION-pivot that fills absent platforms with `0` will
manufacture a false zero for *every* platform whose start date is later than the view's floor. Meta
was simply the only one that qualified. Any new ad platform added to this family inherits the same
defect on day one.

## The positive control — proving a fix without a same-surface before/after

The Daily model already carried an interim **measure-level** patch, so a before/after there would
have been masked either way. The Marketing Model `2d8587b5` reads the same view and **never received
that patch** — it was still showing all 22 literal-zero months.

Refreshing it alone flipped 22 → 0 with the five real months intact to the cent. That proved the
*view* did the work with no measure involved. Only then was the Daily model's patch removed, closing
the drift risk logged when the interim patch went in.

**Pattern worth reusing:** when a fix is masked on the surface you care about, look for a second,
*unpatched* surface reading the same object and use it as the control. See
[[consumer-layer-validation]].

## Two false alarms withdrawn — the `main`-vs-deploy-branch trap

⚠ Item 1 (Sponsored Display) reported a hazard that **does not hold**, and it reached Jira comment
`35978` and commit `5bd4540` before being caught: that `marketing_dim_platform.sql` was *"two
platforms behind deployed truth"* and deploying it *"would have DELETED live Google Ads and Meta
Facebook Ads"*, plus a second warning about `marketing_fct_activity.sql`.

Both were measured against **`main`**, which is **not a deploy branch**. GEP promotes through
`GEP/development` → `GEP/user-testing`, and `main` trailed dev by 17 commits. On `GEP/development`
both files already defined all five platforms, byte-identical to deployed truth.

**Rule:** check drift against `GEP/development` and `GET_DDL` — never against `main`. A drift check
run against `main` will keep manufacturing false alarms, and a false *"this would delete live
platforms"* warning blocks later deploys for no reason.

Related correction: **there is no CODEOWNERS dead-lock on the GEP path.** `GEP/development` and
`GEP/user-testing` carry **no branch rulesets** at all; the CODEOWNERS + required-review ruleset
applies to `main` only. The long-standing "clients-repo PRs dead-lock" framing is true of `main` and
irrelevant to GEP promotion.

## `XmlaClient._get_model()` — a known trap that was never fixed

`pbi_ops/xmla.py` returned `Databases[0].Model`. The XMLA connection enumerates every database in
the workspace, so the Initial Catalog was ignored and the workspace's **first** database came back
regardless:

```
XmlaClient(..., "Marketing Model", ...)._get_model()  ->  'Data Model'
```

**This was documented across nine boot prompts**, with three scripts deliberately forked to resolve
by name — but the shared helper itself was never fixed, so every call site kept inheriting it and the
only protection was whether the author remembered. One boot prompt records a prior `--apply` landing
on the wrong live model. Fixed to resolve by name (aldc-launchpad `9dcdb59`).

Audit of all 44 call sites: `Databases[0]` is `'Data Model'` in both workspaces and `GEP Prod Models`
holds a single database, so **prod was never affected**; the only object reachable in error is the
Marketing Model. 21 not-exposed, 4 already safe-by-name, 13 never reach TOM, 3 exposed — `cli.py`
(write-capable, runtime-chosen target) and `_gp309_yoy_sweep_all_models.py` (enumerates every
dataset, so its Marketing Model readings were silently the Daily model's — any YoY conclusion from
that sweep is suspect).

⭐ **The durable lesson is not the bug, it is the mitigation pattern that failed.** A trap documented
in nine boot prompts and worked around in three forks still bit a tenth session, because
*per-script memory does not compound — a fixed shared helper does.* When a workaround is being
copied forward repeatedly, that is the signal to fix the thing being worked around.

## Gotchas worth keeping

- **`COPY GRANTS` preserves grants but NOT ownership.** `CREATE OR REPLACE` transfers ownership to the
  executing role — `USE ROLE` the owner first. Objects in one pass can have different owners and then
  cannot run under a single role. See [[snowflake-deploy-grants]].
- **FLOAT sums differ by ~1 ULP between executions.** Before calling a delta a regression, compare the
  deployed view **against itself**: it reproduced the identical `4.656612873077393e-10` difference.
  `EQUAL_NULL` reports CHANGED for values that print identically.
- **Verify at the layer the consumer reads, not the one you changed** — the fix went into
  `MARKETING_EFFICIENCY`; the models read `_MARGIN`.
- **Confirm a refresh actually ran** via `get_refresh_history`. That is what exposed the
  `_get_model()` bug: the Marketing Model showed no run while the Daily model refreshed twice.
- Both models hold their own **imported** copy — a warehouse fix is invisible until refreshed
  (`RefreshType.Full`, then `Calculate` so relationships reprocess).

## Item 3 — the margin identity: a second scoping premise refuted, in the opposite direction

Item 3 was scoped as a warehouse defect — `MARGIN_AFTER_AD_SPEND_USD` NULL for ~22 marketplaces,
repair with `COALESCE(SPEND_USD, 0)`. **That would have been wrong, and the measurement caught it
before any deploy.**

All 6,772 NULL rows are marketplace-days for which the warehouse holds **no ad instrumentation at
all**. `WAREHOUSE.MARKETING_FCT_ACTIVITY_UNIFIED` carries exactly **four** marketplaces — Amazon US,
Amazon CA, Amazon UK (from 2026-03-08), plus the `Unknown` cross-channel pool for Google+Meta. eBay,
Walmart, Target, the eight Shopify storefronts, Amazon Mexico and Amazon Brazil have none. The
coalesce would have published *"ad spend = $0"* across 23 marketplaces whose true verdict is
`NOT-RECORDED` — including DTC storefronts bought with the $269,851.28 of Google and Meta money we
**do** collect. ⭐ **That is item 2's Meta false-zero defect rebuilt in the opposite direction.**
The NULLs were correct. No warehouse write was made; the item-3 write approval went unused.

**The real defect was scope, in the field list.** Three plain column sums over three different
populations, in one display folder, with names that invite subtraction:

| measure | rows summed | total |
|---|---|---|
| `Contribution Margin (USD)` | 8,534 | 39,179,520.39 |
| `Margin After Ad Spend (USD)` | 1,762 | 35,034,954.97 |
| `Spend (USD)` | 3,292 | 2,857,131.21 |

`CM − MAAS − Spend = 1,287,434.21`, decomposing **exactly** (residual-of-residual 1.4e-08) into
`+1,533,657.52` margin without ad measurement and `−246,223.31` cross-channel spend without margin.
Restricting the numerator to the rows the subtrahend is defined on closes it to −9.1e-08.

**Delivered** (additive, both live models, no warehouse write, no refresh):
`Contribution Margin (Ad-Measured) (USD)`, `Margin Outside Ad Measurement (USD)`,
`Ad Spend Outside Margin Scope (USD)`, `Margin Identity — Reconciliation` (proven able to **fail**
via a negative control — unlike B7's vacuous guard), and `Margin ROAS` repointed
**13.712888 → 14.418687** (measured first: it appears in 0 visuals of report `15128c39`).

⚠ **The published ~$2,136 "unexplained" residual was a grain artifact, not a third defect.** The
earlier decomposition filtered whole *marketplaces*, which cannot see Amazon UK — the one marketplace
that is mixed. At row grain the decomposition needs two terms and closes with no remainder.
**Generalises: when a decomposition almost closes, suspect the instrument's grain before positing
another cause.** Same class as [[GP-296]]'s monthly-vs-daily walk.

## The lesson that cost the most: a fix pass reintroduced the defect it was fixing

The five new measures went onto the Daily model **unguarded**, while its 20 pre-existing Marketing
Efficiency measures are wrapped in the hidden `__ME Answerable` helper. On a Product/Brand/Vendor
axis each would have printed the **grand total against every member** — B1, the crux defect of this

It was caught only because the follow-up script **asserted the live expression before overwriting
it**, and that assertion failed on a wrapper it did not expect. Nothing downstream would have found

⭐ **Rule: before adding a measure to a table, read what that table's other measures are wrapped in,
and make a fabricated-member test part of verification.** A fabricated ASIN must return BLANK.

## 2026-08-17 — re-verifying the sweep corrected four published claims

A 5-lens sweep on 2026-08-14 filed 19 findings (B20–B33). Two were left for the next session to
re-verify because they contradicted what was already on the ticket. Re-verifying them, and then
extending the same method, corrected four things — **two of which change a remedy.** Everything below
is query-layer/TOM or read-only Snowflake; **no rendered check was performed and nothing was written.**

### The idiom was the defect, and it was 10× bigger than filed

`__GASP Answerable` was confirmed returning the whole-account `82,135.29` as **one distinct value on
every member** of six axes. But the sweep's *reason* was wrong, and the correction generalises:

⭐ **Filter propagation, not graph adjacency.** The six tables ARE graph-adjacent to the host. Every
relationship on this model is `OneDirection` with each fact on the **many** side, so filters flow
dim→fact only and **one fact can never filter another**. An undirected reachability walk calls them
"reachable" and would argue the finding away.

Applying that across all four guards found **70 confirmed holes, not the 7 filed** — `__GASP` 23,
`__ME` 16, `__MEP` 16, `__Sales` 15, each confirmed behaviourally as well as structurally. 70 visible
measures inherit these guards (5/24/3/38), which is **55% of the model's 127 visible measures**.

Two design lessons, both of which would have broken the fix:

* ⭐ **New terms must use `ISFILTERED`, never `ISCROSSFILTERED`.** `ISCROSSFILTERED('T')` is true when
  T *or anything related to T* is filtered. Most added tables hang off `Date`, so naming them under
  `ISCROSSFILTERED` would blank **every ordinary date pivot** — the trap the T6 pass hit, and the
  reason working guards mix the two operators.
* ⭐ **Structure proposes, behaviour decides.** `Consolidation` and `Periodicity` were structurally
  inert on `Order Line` but measurably **split** it (2 and 9 values) — they filter through DAX, not a
  relationship. A guard generated from the relationship graph would have over-guarded both.

See [[answerability-guard]] and [[reference_dax_answerability_guard_idiom]]. ⚠ The fix closes today's
70 holes but the idiom is still a refuse-list, so a table added tomorrow is unguarded again. DAX cannot
enumerate filtered tables, so the durable control is running the census **as a test**, not a cleverer
expression.
