# ALDC-1192 — GEP **Prod** model reads `TEST_DG1_GEP` on the **non-prod** Snowflake account

**Type:** Bug | **Status:** 🔴 To Do (blocking) | **Priority:** Highest | **Project:** ALDC Scrum
**Sprint:** S11: DL Cortex Perf | **Assignee:** Paul Russell
**Relates to:** [[ALDC-1191]] (found during; now blocked by this), [[ALDC-1164]], [[GP-281]]

## The finding

Two tables in the **client-facing prod** model `GEP Prod Models / Data Model` (`74a529b3`) source
from the **non-prod** account `og35375`, out of the literal `TEST_DG1_GEP` database, because their M
hard-codes host and warehouse instead of using the model's parameters.

The 34 healthy tables parameterise it:

```
Snowflake.Databases(SNOWFLAKE_HOST, SNOWFLAKE_COMPUTE)
  -> Source{[Name=PARAM_SHORT_CODE, Kind="Database"]}
```

`Campaign` and `Platform` do not:

```
Snowflake.Databases("og35375.canada-central.azure.snowflakecomputing.com","COMPUTE_WH")
  -> TEST_DG1_GEP -> WAREHOUSE -> MARKETING_DIM_CAMPAIGN  (View)   [Campaign]
  -> TEST_DG1_GEP -> WAREHOUSE -> MARKETING_DIM_PLATFORM  (View)   [Platform]
```

`Campaign` carries **150,053 rows**; `Platform` 5. Both partitions are state 1 and refreshed in the
last successful run, so they are **live, not vestigial**.

⭐ **A datasource listed under `GET /datasets/{id}/datasources` proves only that the model DECLARES
a source — not that any table queries it.** The evidence is the partition M
(`$SYSTEM.TMSCHEMA_PARTITIONS.QueryDefinition`), and checking that was what turned this from
"a stray binding" into a live defect. [[ALDC-1164]] had noted the og35375 binding existed and warned
against touching it, but never established which tables used it.

## Why it matters

1. **Provenance.** Prod client figures originate in the account where dev work happens. A change to
   `TEST_DG1_GEP.WAREHOUSE` moves numbers on a client's prod report with no prod deploy and no
   review. Compounds [[GP-281]] (TEST clone staleness).
2. **Separate credential, separate blast radius.** `og35375` has its own credential object
   (`2f0ade5e`) and its own Phase 3 timeline, so these two tables fail or survive independently of
   the other 34 — and a half-populated model still reports **Completed**.
3. **It blocks [[ALDC-1191]].** After the `wj66376` credential was fixed, GEP's refresh fails on
   *this* account. These two partitions are the only thing keeping a client-facing prod model down.

## ⛔ The obvious fix is a data regression — do not just repoint

Prod equivalents exist in `PROD_DG1_GEP.WAREHOUSE` (neither is in `REPORT_COMMON`) but **do not
match**:

| Table | In model now (TEST) | PROD equivalent | Delta |
|---|---:|---:|---:|
| `Campaign` / `MARKETING_DIM_CAMPAIGN` | 150,053 | **144,729** | −5,324 (−3.5%) |
| `Platform` / `MARKETING_DIM_PLATFORM` | 5 | **2** | **−3** |

`Platform` 5 → 2 would plausibly drop whole platforms out of marketing visuals.

⭐ **TEST holds MORE than prod, which reads as a deliberate shim** — marketing dimensions delivered
into the prod model ahead of the prod warehouse having them, consistent with the marketing work
([[GP-226]] / GP-319) being TEST-first. If so, repointing **regresses** coverage rather than
correcting it. Stated as inference from row counts + ticket history, not established fact; confirm
against the marketing roadmap before choosing.

## Options

| # | Action | Restores GEP | Cost |
|---|---|---|---|
| A | Repoint both partitions to the parameterised prod source | ✅ fast, metadata-only | **Changes client data** (above). Likely visible regression. |
| B | Fix og35375 auth — register a key, switch `2f0ade5e` to KeyPair | ✅ **no number moves** | Needs a Snowflake mutation on non-prod. Preserves the defect. |
| C | Deploy the missing marketing dim content to `PROD_DG1_GEP.WAREHOUSE`, then repoint | ✅ correct end state | Warehouse deploy; slowest. |
| D | Nothing | ❌ | GEP serves the 16:08Z snapshot; renders, but stales silently. |

**Chosen 2026-09-09: B to restore, C as the real fix.**

## og35375 is under the same enforcement — MEASURED

Single-shot attempts (one per user, capped, stop-on-success, nothing locked out):

| User | Result |
|---|---|
| `PAULRUSSELLADMIN`, `paulrussell` | **MFA with TOTP is required** |
| `SNOWFLAKE_ADMIN`, `ALDC_ADMIN`, `TEST_DG1_CORE_ADMIN` | incorrect username or password |

⭐ **The MFA error is the informative one — it means the password was ACCEPTED** and the second
factor is the wall. So `PERSON` accounts on og35375 are MFA-gated.

⚠ It also retires an earlier "og35375 is probably converted" reading: the first `connect_nonprod()`
failure was never evidence, because that helper only tries an **MFA-gated PERSON account** and a
**stale KV copy** (yesterday's `TEST_DG1_CORE_ADMIN` rotation updated the *wiki vault*, not Key
Vault). **A helper's failure is only evidence about what the helper actually tried.**

**Consequence: no automated route into og35375 exists.** Registering a key needs `ALTER USER` in an
authenticated session, and a second factor cannot be supplied programmatically — so option B has an
irreducible human step.

## Option B state

Key pair generated; **private** half in `aldc-vault-test` / `snowflake-keypair-nonprod-pbi`.
Public-key fingerprint `SHA256:yXwf4OPR1b/jvk4n1XeJ7t0wDQmfuD/ulZj6bYDhxGs=`.

⛔ **`az keyvault secret set --value <pem>` SILENTLY TRUNCATES at the first newline.** The first
store left a **27-character stub** (the PEM opening header and nothing else) while the script
reported "stored, 1704 chars" from its own local variable. Caught by reading back and loading it
(`chars: 27, USABLE: NO — MalformedFraming`). **Use `--file`.** The prod entry
`snowflake-keypair-SERVICE-POWER-BI` reads `has_real_newlines=True`, i.e. written by another route.
Re-stored and verified: 1,703 chars, PKCS8, real newlines, fingerprint matches.

Runbook for the human step:
`aldc-launchpad/docs/evidence/aldc1191/ALDC-1192-option-B-snowsight-runbook.md` — discover the PBI
user from `LOGIN_HISTORY` (`ODBC_DRIVER`/`GO_DRIVER` are only Power BI), confirm
`RSA_PUBLIC_KEY_FP` is NULL, `SET RSA_PUBLIC_KEY`, confirm the fingerprint. Rollback
`ALTER USER … UNSET RSA_PUBLIC_KEY`.

⚠ The wiki's own [[snowflake]] page lists `EXCELBISERVICE` as a "Power BI service account" with
environment `—`. **Unconfirmed for og35375** — a hypothesis for step 1 to test, not a target to
adopt.
