## Problem

## ⭐ The corrected premise — this one matters

The report was first assessed as **"I don't think this is us."** **That is refuted.** The error
string is emitted by our own code:

| Where | What |
|---|---|
| `core_api/v1/func_common.py:92` | `f"Environment Variable {variable_key} improperly set. Value required or improper value assigned."` |
| `core_api/v1/func_common.py:98` | `environment_error = f"Environment variable setup failed - {e}"` |

Grepped every local repo: the string exists in **no repo except `core_api`**. The client's daemon
received our error text as a **return value** (note the f-string `{sub_sales_detail_extract}` in
their traceback) and wrapped it in its own exception — which is exactly what made it look
client-side.

**Lesson:** an error surfaced *by* a client's system is not evidence the error *belongs to* it.
Grep for the string before assigning blame. See [[core_api]] gotchas.

## What we know (executed evidence)

### 1. The insertion-order signature narrows the fault to ONE variable

`func_common.py` populates a single dict then loops:

```python
for variable_key, variable_value in environment_variables.items():
    if variable_value == None:
        raise ValueError(f"Environment Variable {variable_key} improperly set. ...")
```

Python preserves insertion order, so **the error names the first absent variable.**
`azure_client_id` is key **#21** — therefore every nullable key before it *was populated*:

`cosmos_database, cosmos_hostname, cosmos_key, environment_level, environment_location,
environment_version, encryption_key, master_client_id, master_client_secret, pushover_token,
sys_storage_name, storage_sas1, twilio_sid, twilio_token, twilio_number, azure_subscription_id`

**This is not a cold container or an env wipe** — Cosmos, Twilio and Pushover were all set. It is a
config that lost *specifically* `AZURE_CLIENT_ID`. Keys **#22+** (`azure_tenant_id`,
`azure_client_secret`, `mailjet_*`, `azure_deployment_resource_group`, `GPT_KEY`, `GPT_ORG`) were
**never tested** — the loop short-circuits. They must be verified separately; their health is
UNKNOWN, not proven.

> This is a reusable diagnostic: any `func_common.py` env error tells you the **exact prefix of the
> dict that was healthy**, for free.

### 2. `== None` tests absence, not blankness

An empty string `""` **passes** the check. So the variable was genuinely **absent** from the process
environment. That rules out mechanisms which yield an empty value — notably `docker compose` with
`KEY: ${VAR}` and `VAR` unset, which resolves to `""`.

### 3. The blast radius is EVERY route, and it is sticky per process

`environment_error` is a **module-level global evaluated once at import**:

- `v1/__init__.py:272` — `environment_error = func_common.environment_error`
- `v1/__init__.py:302` — the **first statement in the request `try`, before any auth check or route
  dispatch** — `if environment_error: raise ValueError(environment_error)`

So while a worker process holds a bad config, **every function/option fails**, not just
sales-detail — and it stays broken for the life of that process. Only a restart re-imports.

### 4. A total config failure is served as HTTP 200 "success" ⚠

`v1/__init__.py:1244-1247`:

```python
except Exception as e:
    if environment_error:
        response_dict = func_common.form_response(
            f"{route_function}/{route_option}", 200, "success", f"success", environment_error
        )
```

Status **200**, literal string **"success"**, error in the payload. Two consequences:

1. It explains the client traceback's shape — they got a *string*, not an HTTP error.
2. **Any monitor watching status codes sees green** during a total outage. This is why a client
   email was the detection mechanism.

### 5. Legacy vs FastAPI optionality divergence

`core_api/api/__init__.py` (`GlobalConfig`, the FastAPI rewrite) declares
`azure_client_id: Optional[str] = None` — and likewise `pushover_token`, `twilio_*`, `gpt_key`,
`gpt_org`. The legacy `func_common.py` treats **all ~26 as mandatory**. `azure_client_id` is
load-bearing in only `route_setup.py:547,590,676` (`ClientSecretCredential`) and
`v1/keyvault_client.py`. So a peripheral Azure credential is a hard prerequisite for routes that
never touch Azure — the FastAPI path already models this correctly.

### ⭐ ALDC-1002's fix and legacy `func_common`'s contract are mutually exclusive

`v1/keyvault_client.py` **at the deployed SHA**: line 12 docstring requires *"Function App managed
identity with 'Key Vault Secrets User' role"*; line 45-48
`SecretClient(..., credential=DefaultAzureCredential(), ...)`; line 119 **eagerly initialised at
import**.

But in the installed `azure-identity` SDK (`azure/identity/_credentials/default.py`, read directly):

| line | what |
|---|---|
| 149 | `credentials.append(EnvironmentCredential(...))` — **first in the chain** |
| 121-122 | `managed_identity_client_id = kwargs.pop(..., os.environ.get(EnvironmentVariables.AZURE_CLIENT_ID))` |
| 162-164 | `ManagedIdentityCredential(client_id=managed_identity_client_id, ...)` |
| 71-74 | docstring: *"The client ID of a user-assigned managed identity. Defaults to the value of the environment variable AZURE_CLIENT_ID, if any."* |

So **while `AZURE_CLIENT_ID` is set the managed identity granted the KV role can never be used** —
`EnvironmentCredential` wins with the service principal, *and* the managed-identity fallback is
poisoned because it asks IMDS for a user-assigned identity whose client ID is an SP app ID. The SDK
says it outright (`azure_arc.py:52`): *"DefaultAzureCredential ensure the AZURE_CLIENT_ID
environment variable is not set."*

**⇒ To make ALDC-1002 work in place you must REMOVE `AZURE_CLIENT_ID` — which detonates
`func_common.py:89-93` and takes the whole v1 API down, reported as HTTP 200 "success".**

**Corroborating motive, same day:** PR #257 (**ALDC-1143**, open, *"Azure Functions warmup trigger
for KV credential pre-warming"*) created 2026-09-08T16:00:18Z, still updated at **23:19:49Z**
(i.e. work continued *after* the incident); body cites *"Forces `ManagedIdentityCredential`"* and
*"Found during prosecution review of PR #255"*; CI failed ~11 times that afternoon. A
`workflow_dispatch` deploy ran at **18:49:25Z**, 2h57m before the error. Someone was pushing on
exactly this collision in the hours around it. **Not yet proven** as the triggering action — needs
the app-settings check.

### ⭐ Why 21:46 and not earlier — and why my probes were clean

Both slots reference the **same mutable tag** `ghcr.io/aldc-io/core-api:2.0.0-eclipse-2-1.1`,
measured identical across three build runs (09-02, 09-05, 09-08). So **prod picks up new code on any
restart or scale-out, with no slot swap at all** — and a fresh process **re-imports `func_common`
and re-reads the environment**. Because `environment_error` is import-time and per-process, a config
defect stays invisible on warm workers and surfaces only on workers started after it. **A mixed
population is exactly what produces "client fails at 21:46, 25/25 probes clean at 23:00."** The
Gate 3 caveat now has a concrete generator; treat prod as **UNKNOWN, not healed**.

⚠ Related: the rollback-safety gate at `deploy_az_webapp_container.yaml:73` compares
`STAGE_IMAGE != PROD_IMAGE` — but the tag never changes, so **it compares a constant to itself and
cannot fail.** It passed on both `push` runs where `force_deploy` was false. Reinforces [[ALDC-994]].

### The HTTP 200 finding is worse than §4 above

`status_code` occurs **exactly once in the whole 74KB `v1/__init__.py`** — line 1281, hardcoded
`status_code=200`. So it is not "the config path returns 200": **every v1 response is HTTP 200**,
including the 400 and 500 branches. A status-code monitor is blind to **100% of v1 errors**. Line
1247 *additionally* overwrites the body's `code`/`type`/`message` with `200`/`success`/`success`,
blinding body-parsing monitors on this path too. Two independent cannot-fail layers.

### `azure_client_id` is NOT on the failing path

Enumerated census of runtime reads: `func_common.py:41` (discarded — line 57 re-inits the dict),
`:78` (**the only reason it is mandatory**), and `route_setup.py:547/590/676`, all three inside
`setup_azure_*` provisioning functions at call time. **Zero** reads in `route_dataset`,
`route_warehouse`, `route_report`, `route_explorer`, `route_capacity`, `route_schedule`. The blanket
loop is the sole reason a provisioning-only credential gates the whole API.
**Correction to §5 above:** `keyvault_client.py` does **not** read `azure_client_id` — only
`KEY_VAULT_URL` (line 38) and `ENVIRONMENT_LEVEL` (line 96). Its dependency is the *implicit* SDK
one, which is the more interesting thing.

### Refuted — do not spend time here

- **#3 unresolved Key Vault reference — REFUTED.** An unresolved `@Microsoft.KeyVault(...)` leaves
  the setting **present** carrying the literal reference string, so the loop **passes**. The symptom
  requires genuine *absence*.
- **#5 on-prem `core-api-2.1` — REFUTED by the ordinal.** Verified programmatically: the dict has
  **30 keys**, `azure_client_id` = **#21**, `environment_location` = **#6**. `compose_on_prem.yaml`
  has no `env_file:` and declares only 21 vars, omitting `ENVIRONMENT_LOCATION` — so as committed it
  could only ever name `environment_location`. The ordinal also **narrows the host**: naming #21
  requires all 20 preceding nullable keys populated, i.e. an App Service-style settings blob.
  ⚠ **Side finding worth its own ticket:** if that container *is* running, it has been returning
  `Environment variable setup failed - environment_location improperly set` as HTTP 200 "success" to
  every request since deployment. Nobody has probed port 6661.

### ⚠ Read before fixing

**Re-adding `AZURE_CLIENT_ID` restores the API and silently re-breaks ALDC-1002's KV path.**
`get_private_key()` swallows failures to `None` (`keyvault_client.py:73-74, 84-86`) → Snowflake
falls back to password auth → **ALDC-1098** (password-fallback removal) would hard-fail on deploy.
**Fixing this at the app-settings layer alone guarantees the next outage.**

Durable fix is code: split the dict into `REQUIRED` (keeps the raise) and `OPTIONAL` (warns), **with
a hard check at each point of use** — roughly **10 genuinely required / 15 safe to demote**. Do not
just delete the loop, and **do not copy `GlobalConfig` as the template**: it makes
`environment_level` optional, which 12 call sites including `route_auth` depend on. Measured
divergence: **16 of 25** legacy-mandatory vars are `Optional` in `GlobalConfig`, 1 diverges the
other way, and **3 `GlobalConfig`-mandatory vars the legacy loop never checks at all**
(`storage_account`, `jwt_secret`, `allowed_origins`).

On the status code: fix **line 1247** first (a config failure is not `"success"`). Treat **line
1281** as a separate coordinated change — honouring `response_dict["code"]` is a **breaking change
for every existing caller**, including the client's `InsiteDaemon`, which we cannot modify.

INCIDENTAL: `api/__init__.py:59-65` `get_global_config()` calls **`os.abort()`** on validation
failure — SIGABRT at import, a crash-loop. Loud rather than silent, so better, but that is a **third
distinct behaviour** for the same condition in one codebase.

## Likely causes (ranked — ⚠ superseded by the correction above; #4 withdrawn, #3 and #5 refuted)

1. **Slot swap / stage↔prod config drift** — `deploy_az_webapp_container.yaml` deploys to
   `slot-name: stage`; settings not marked slot-sticky travel with a swap. Directly the risk
   [[ALDC-994]] exists to remove. ⚠ Must first confirm the prod **Function App** even has a `stage`
   slot — consumption-plan Function Apps often don't, which would kill this outright.
2. **A config edit / restart** at ~21:46 UTC — Azure Activity Log.
3. **Unresolved Key Vault reference** (`@Microsoft.KeyVault(...)`) — secret rotated/disabled, or the
   managed identity lost `get`.
4. **ALDC-1002** (`pr-255`, Snowflake key-pair auth via Key Vault, adds `v1/keyvault_client.py`) —
   but it is an **open PR branch** and `func_common.py`'s env list has *not* changed recently (last
   touch `dd26f2b`). The code's *requirement* did not change → points at the environment side.
5. **A different core_api instance entirely** — qa/test Function Apps, or the on-prem
   `core-api-2.1` container (`compose_on_prem.yaml`, `6661:80`, GitHub env "On-Prem"). All run the
   same code and emit the identical string.
6. **Multi-instance/worker skew** — only some instances hold the bad config.
