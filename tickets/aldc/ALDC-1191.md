# ALDC-1191 — Snowflake Phase 3 landed on `wj66376` and killed both prod PBI models

**Type:** Bug | **Status:** 🟠 Partially fixed | **Priority:** Highest | **Project:** ALDC Scrum
**Sprint:** S11: DL Cortex Perf | **Assignee:** Paul Russell
**Relates to:** [[ALDC-1164]] (the migration this pre-empted), [[ALDC-1192]] (blocks the GEP half),
[[ALDC-1002]] (should be reopened)

## What happened

Both live client-facing Power BI prod models began failing scheduled refresh at
**2026-09-09 ~17:00Z**, with byte-identical text:

> `ModelRefresh_ShortMessage_ProcessingError` — The credentials provided for the Snowflake source
> are invalid. (Source at `wj66376.canada-central.azure.snowflakecomputing.com;COMPUTE_WH`.)

| Model | Last success | First failure |
|---|---|---|
| GEP Prod Models / Data Model (`74a529b3`) | 16:01→16:08Z | **17:01:15Z** |
| FUSION_92 Prod Models / Activation Model (`cf8333e6`) | 16:00→16:03Z | **17:00:28Z** |

They fail together because they share **one** credential object (`79d103a2…`) — established on
[[ALDC-1164]] the day before.

## ⭐ Root cause — the platform did it, not a person

`SHOW USERS` on `wj66376`: **17 `LEGACY_SERVICE` users on 2026-09-08 → 0 on 2026-09-09.** All 20
non-person users are now `TYPE = SERVICE` with `has_password = false`. `PERSON` users kept their
passwords. `SHOW AUTHENTICATION POLICIES IN ACCOUNT` → **0 rows**, so this was not a policy attach.

Corroborated by Snowflake's own tasks visible in the account:

```
2026-09-13 07:41  SCHEDULED  SECURITY_ESSENTIALS_STRONG_AUTH_LEGACY_SERVI…
2026-09-13 07:41  SCHEDULED  SECURITY_ESSENTIALS_STRONG_AUTH_PERSON_USERS
2026-09-09 18:50  SCHEDULED  THREAT_INTELLIGENCE_PASSWORD_SERVICE_USERS_T…
```

**Conversion window:** last successful password auth anywhere on the account **09:15:15 PDT**;
first failure **10:03:05 PDT**. A 48-minute window.

⭐ **Phase 3 STRIPS THE PASSWORD rather than blocking the login.** The resulting error is
`390100 INCORRECT_USERNAME_PASSWORD` — indistinguishable from a rotated password, which is why
"someone rotated it" was the wrong first read. See [[vacuous-verification]].

⭐ **A `SERVICE` user cannot hold a password, and no admin can restore one.** Snowflake's
`CREATE USER` reference defines `LEGACY_SERVICE` as *"similar to `SERVICE`, but allows password and
SAML authentication"* — password auth is the property `SERVICE` lacks. So "can Tami reset it?" has
a definitive no: it is a type constraint, not a permission. Reverting to `LEGACY_SERVICE` is what
Phase 3 removes, and the conversion task is scheduled to run again **2026-09-13**.

## The blind-instrument trap

Both credentials available for diagnosis were passwords — `SERVICE_POWER_BI` (via PBI) and
`prod-dg1-core-admin` (via KV) — and **both were rejected**, so the mechanism could not be measured
at all until a key-pair session was established (`snowflake-admin-prod-keypair`). Key Vault metadata
proved the stored secret was untouched since 2026-06-03, which is what showed the change was
Snowflake-side rather than a stale local copy.

⭐ **Vault metadata (`attributes.updated`) is a cheap, powerful discriminator** between "our copy
drifted" and "the remote object changed" — and it needs no secret retrieval.

## Fix — FUSION_92 done, GEP blocked

Credential `79d103a2` switched `Basic` → `KeyPair` at **18:11:33Z**. See [[power-bi]] for the exact
working request shape; two facts cost real time:

- **Only the legacy `/gateways/{gw}/datasources/{id}` surface works.** Fabric
  `PATCH /v1/connections/{id}` returns bare `InvalidInput`.
- **`passphrase` is REQUIRED even for an unencrypted key.** The API says so precisely:
  *"a property with a null value … Property name: passphrase."*

Verified at the source: **44 `RSA_KEYPAIR` logins on `GO_DRIVER 2.1.0`**, first one 10 seconds after
the write. `GO_DRIVER` confirms **ADBC is now live**, so the count-distinct risk became real.

| Model | Outcome |
|---|---|
| FUSION_92 / Activation Model | ✅ **fixed** — 4 sustained scheduled refreshes, parity **15/15** |
| GEP / Data Model | 🔴 **down** — fails on `og35375`, see [[ALDC-1192]] |

## ⛔ The alarm went quiet — as predicted

After **5** consecutive failures the GEP schedule **auto-disabled itself** (`enabled: False`), and
`MailOnFailure` emails stop at that point. This is the detection gap flagged on [[ALDC-1164]],
realised within a day.

⭐ **Fixing the credential is therefore NOT sufficient for GEP — the schedule must be manually
re-enabled**, or the model never refreshes again even with working auth. Alarm on **staleness**,
never on `Failed`.

## Parity gate (the real acceptance test)

Because ADBC's open `count distinct` defect returns wrong numbers *while the refresh Completes*,
a green refresh is not evidence. Metrics were frozen to closed history (rows dated
`< 2026-09-01`, which cannot legitimately move) and compared across the driver switch:

| Table | Metric | ODBC | ADBC |
|---|---|---:|---:|
| Spend | frozen rows | 1,032,601 | 1,032,601 |
| Spend | distinct `FLIGHT_KEY` | 7,752 | 7,752 |
| Spend | distinct `PLATFORM_KEY` | 50 | 50 |
| Flight / FCT_FLIGHT | distinct `FLIGHT_KEY` | 14,634 | 14,634 |

**15 assertions, 0 mismatches, 0 unmeasured.** The ADBC defect did not manifest on this model.

## ⚠ Two of my own verification failures, both silent

Recorded because both would have shipped a false "fixed", and both were caught only by reading
state back rather than trusting a success response. Written up as new shapes in
[[vacuous-verification]].

1. **The PBI `PATCH` returned HTTP 200 with `credentialType` unchanged** at `Basic` on the first
   attempt. A 2xx is not proof a write took.
2. **The parity gate printed "GATE PASSED" on 2 assertions with 13 NOT-MEASURED.** Cause: the
   baseline merge let an *unvalidated* date column (integer surrogate keys — `SPEND_DATE_KEY`,
   `START_DATE_KEY`, `DATE_KEY`) override an *execution-validated* one, and the verdict logic asked
   only "any mismatches?" and never "did I see anything?". ⭐ **Coverage belongs IN the verdict**:
   a pass now requires 0 mismatches **and** 0 unmeasured.
3. **`az keyvault secret set --value <pem>` truncated at the first newline** — Key Vault held a
   27-character stub while the script reported "stored, 1704 chars" from its own local variable.
   **Use `--file` for any multi-line value.** See [[ALDC-1192]].

## NOT done

- **GEP is down**, blocked on [[ALDC-1192]]; its schedule needs manual re-enabling after the fix.
- **No rendered/consumer-layer validation on either model.** All three instruments were unavailable:
  Chrome extension not connected; `ExportTo` → `FeatureNotAvailableError` (Export to File is not
  enabled on this **PP3** capacity); Playwright would hit the login wall. FUSION_92 is
  **numerically verified, not render-verified**. Precedent: [[GP-293]].
- **GEP parity is NOT-MEASURABLE** until its refresh succeeds — its resident data is still the
  pre-cutover ODBC load, so a comparison would pass vacuously.
- `PROD_DG1_CORE_SVC_9AC36447` **still down** — zero key-pair logins ever; key staged since 09-07,
  client never switched. `_DA8904DB` and `_8B28D977` have residual failing password paths.
- **Trust Center enforcement date still never read** — the open `next:` from [[ALDC-1164]], and now
  relevant to whether 09-13 is the next wave for `PERSON` users.
- Evidence scripts uncommitted, on the wrong branch (`docs/fu92-429-datastore-versioning`).
