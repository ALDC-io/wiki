# ALDC-1164 — Migrate SERVICE_POWER_BI Snowflake auth off password

Power BI refreshes from Snowflake prod (`wj66376.canada-central.azure`) as the
`LEGACY_SERVICE` user `SERVICE_POWER_BI`, authenticating with a **password over ODBC**.
Snowflake Phase 3 converts `LEGACY_SERVICE` → `TYPE=SERVICE` and blocks password auth
entirely. Assigned Paul, reported by Tamara Krasnova, priority Highest.

Investigated 2026-09-08 with a 5-lens `prospect` council plus direct read-only measurement
of the Power BI REST API, the Fabric Connections API, and Snowflake `wj66376`.
**Nothing was changed in Power BI, Fabric, or Snowflake.**

## ⭐ The measured picture (2026-09-08)

**`SERVICE_POWER_BI` is the last unprotected service user on prod.** Of **17**
`LEGACY_SERVICE` users on `wj66376`, **16 have `has_rsa_public_key = true`. Exactly one
does not.** [[ALDC-1002]] covered the whole `PROD_DG1_*` estate; Power BI is the single
straggler — which confirms the ticket's framing as an ALDC-1002 scope gap.

account.** This is a deadline, not an outage.

## Corrected premises (the deliverable)

1. ⭐ **"Power BI's ODBC connector does not support Snowflake key-pair" — FALSE since 2025.**
   Connector implementation 2.0 (GA July 2025) swapped Simba ODBC for the Arrow **ADBC**
   driver; **Key Pair Auth (ADBC)** and **Service Principal (SPN)** are supported, key-pair
   GA Feb 2026. Confirmed against our own tenant — `GET /v1/connections/supportedConnectionTypes`
   returns for `Snowflake`:
   `supportedCredentialTypes: ["Basic","OAuth2","KeyPair","ServicePrincipal","WorkspaceIdentity"]`.
   Of **325** connection types, only **two** declare `KeyPair`: `SFTP` and `Snowflake`.
2. ⭐ **Entra External OAuth — the ticket's recommended path — is the weakest option.**
   Snowflake's own partner-authentication matrix marks **External OAuth = "No" for
   `TYPE=SERVICE` on PowerBI Cloud**, key-pair **"Yes"**. And OAuth set via the PBI REST API
   carries no refresh token: *"credentials can only be used for one hour"* — unautomatable
   for scheduled refresh.
3. ⭐ **"38 NAVIRA dashboards" is refuted.** The whole visible estate contains **1 dashboard**.
   "NAVIRA" resolves to one object: `Navira MAP Violators Model`, a *dataset*, in *GEP Sandbox*,
   on **`og35375` (non-prod)** — outside the ticket's scope entirely.
4. **Azure Key Vault cannot hold this secret.** `KeyPairCredentials` has fields
   `identifier` / `privateKey` / `passphrase` and **no `privateKeyReference`**. KV indirection
   exists for `Basic`, `Key`, `SAS` and `ServicePrincipal` — not key pairs. Fabric holds its
   own copy regardless. See [[snowflake-auth-phase-3]].

## ⚠ The risk to price: key-pair forces ADBC

*"if you're using Key Pair authentication, the ADBC driver is always used regardless of
this setting."* Consequences:

- It **deletes the documented ODBC fallback** (`remove Implementation="2.0"`), which is
  Microsoft's own self-mitigation for every other ADBC problem.
- It inherits two **still-open** connector defects: *"`count distinct` returns incorrect
  result"* and a memory regression. The first is a **silent wrong-number** failure — it
  **Completes**, so `notifyOption: MailOnFailure` cannot fire on it by construction.
- Both live models sit on capacity **`PP3` (Premium Per User)**, where Microsoft's prescribed
  remedy for the memory defect ("increase the memory of the Premium capacity") is impossible.
- Mitigating: today's sessions show **ODBC 3.2.2, not ADBC** — the defect is not currently
  live. But MS's ODBC→ADBC transition runs late Q3/early Q4 2026 with **no permanent opt-out**,
  so it arrives regardless.

⭐ **Therefore any cutover MUST include an old-vs-new numeric parity check (row counts + a
distinct-count measure). A green refresh is not evidence of correct numbers here.**

## The zero-blast-radius validation path

`POST https://api.fabric.microsoft.com/v1/connections` creating an **unbound
`ShareableCloud`** connection. The tenant declares `supportsSkipTestConnection: false` for
Snowflake, so **creation performs a real authentication attempt** — a success response *is*
the proof, not merely a stored setting. Teardown is one `DELETE`. Nothing bound, nothing at
risk, and **no rollback password needed**.

Prerequisite: register the public key on a throwaway `TYPE = SERVICE` Snowflake user on
non-prod first — which also validates the `TYPE=SERVICE` + key-pair combination Phase 3 forces.

⚠ Do **not** test on connection `2f0ade5e` — despite looking non-prod, it carries
`GEP Prod Models / Data Model`.

## ⚠ Wider finding: "has a key" ≠ "uses a key"

`PROD_DG1_CORE_SVC_DA8904DB` has `has_rsa_public_key = true` **and authenticated by Password
today** (~15 sessions, 14:48–14:50, PythonConnector 3.12.3). **A registered-but-unused key
does not survive Phase 3.** If that pattern holds across the other seven, [[ALDC-1002]] is
marked Done but is not functionally complete. Needs an audit of *actual authentication
events*, not configuration.

Also outside both tickets: `VLADRYZHKOV`, a `PERSON` account, authenticating by password via
PythonConnector — human accounts used programmatically also need a second factor under Phase 3.

## Method notes worth keeping

- ⭐ **The `Extension` blind zero.** A first enumeration reported `SNOWFLAKE datasources: 0`
  with **0 errors**. Modern connectors report `datasourceType: "Extension"` and leave
  `connectionDetails.server`/`.database` NULL — identity is in `.kind`, target in `.path`.
  Any enumeration must carry a positive control. See [[vacuous-verification]].
- The legacy `/gateways` endpoint returns **0** with HTTP 200 for cloud gateways — not
  "no gateways". Virtual cloud gateway IDs are only obtainable from the dataset→datasources walk.
- The Fabric API types these objects as `"Snowflake"`; `"Extension"` is a **legacy-API
  rendering artefact**, not the object's type.
- `lastCredentialUsedDateTime` on `/v1/connections` is a direct "this credential last
  authenticated at T" signal in one GET — better health check than polling refresh history.
